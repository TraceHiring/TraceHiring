## 4. State machines

### 4.1 Item version (`item_versions.status`)
`draft → in_review` (author or importer; parameterised: variants must exist) · `in_review → approved` (approver, M1-3; AI drafts too) · `in_review → not_approved` (approver, "Send back"; terminal; R5-22) · `in_review → draft` is **not** allowed (an edit is a new version) · `approved → retired` (OW AD RC; a retired version stays valid in already-published snapshots; it cannot be added to pools or new drafts) · imported rows go `draft → approved` in one statement by the importer (Q23) · inline section rows are inserted `approved` (M1 §3.3). Every transition is audited `item.<verb>` `{item_version_id, from, to, self_approved}`.

### 4.2 Test version
D1's `draft → published → retired` unchanged. **New action "Edit"** on a published test: `POST …/tests/:id/versions` clones the latest published version into a new draft (`version_no + 1`, new `ruleset_versions` by the D1 seed trigger, then its `settings` copied from the source ruleset). The one-open-draft index stays. Invitations keep `test_version_id` (D1 immutable column); M2 drives point new invites at a chosen published version.

### 4.3 Import job
`open → validating → completed | failed`; `open|validating → cancelled` (author). Per-row error codes: `missing_field`, `bad_format`, `bad_skill`, `bad_difficulty`, `bad_options`, `bad_key`, `too_long`, `bad_image_ref`, `image_missing`, `image_too_large`, `image_bad_type`, `duplicate_in_file`, `duplicate_in_bank`, `bad_param_spec`, `variant_generation_failed`, `row_limit`. Max 2,000 rows per job.

### 4.4 AI draft job
`queued → running → completed | failed`, and `queued → failed` (a message that disagrees with its row, or the last try; R5-61 e). A job never moves an item past `in_review`.

### 4.5 Member invite
`pending → provisioned | failed`; `pending → cancelled` (admin). Membership `invited → active` (invitee) or `invited → removed` (admin).

### 4.6 Section at run time (DO, package v2; R5-20, R5-21)
States per section: `not_entered → open → closed`. **Untimed versions** (no section has `time_limit_seconds`, M1-11): sections are open together from test start, as in D1 (free order), except that a `forward_only` section still refuses positions below its highest served one and serves the next one only after the `afterSeq` check (R5-45); all close at test submit or the test deadline. **Timed versions:** sections run in `position` order. Section 1 opens at test start; a section opens when the previous one closes; it closes on the first of: its deadline (`opened_at + time_limit_seconds`, events received up to `GRACE_MS` later still count), `section.finish`, the test deadline, or test submit. A closed section never reopens; unused time is lost. The draw happens when a section opens (stored before its first serve, R5-19); a section never opened is never drawn and its `draw_count` slots score 0. The DO's alarm fires at the earlier of the next section deadline and the test deadline. `SessionViewV2.sections[].state`/`deadlineAt` are read from the DO; the client clock never decides.

### 6.3 Parameterised variants (ABH-7)
Grammar (Pratt parser, `packages/item-variants`): numbers (integers and decimals ≤ 6 places), parameter names `[a-z][a-z0-9_]{0,15}`, `+ - * / ^` (integer exponent 0–6), parentheses, functions `min max abs round(x, d) floor ceil gcd lcm`, comparisons and `and/or/not` in constraints only; max 200 chars, max depth 16; anything else is a parse error. Arithmetic is exact rational (`bigint` numerator/denominator); division by zero rejects the candidate tuple. Templates substitute `{{name}}` or `{{name:fmt}}` (`fmt` = decimals 0–4, or `%`). Generation: PRNG `sfc32` seeded with the first 128 bits of `SHA-256(item_version_id ‖ variant_no)`; draw parameter tuples, evaluate derived values and constraints, render stem and options; reject a tuple that violates a constraint, renders two equal options, or duplicates an earlier variant; stop at `count` accepted variants or 50 × `count` attempts (`variant_generation_failed`). Each variant's difficulty = the parent's unless the author sets one (±0.10 enforced by the DB). The DO picks a variant per candidate with the session-seeded stream (§6.5); the chosen `itemVariantId` is mirrored. **Share metric:** `GET …/bank/stats` returns, per org (and for the library), `quant_items_approved` and `quant_items_parameterised` with `share = parameterised / approved` for `skill_key = 'quant'`; this is the ABH-7 "≥40%" measurement (content target deferred, §13).

### 6.4 AI drafting with human approval (ABH-8)
`POST …/bank/ai-drafts` (OW AD RC) → `ai_draft_jobs` row + Queue `trace-authoring` message `{ jobId, orgId, workspaceId, format, skillKey, difficulty, count, topic }`. The topic is scrubbed before enqueue (emails, phone-like digit runs ≥ 8, URLs replaced by `[removed]`) and capped at 500 chars. Consumer (`workers/jobs/src/drafting/`, role `trace_authoring_worker`): calls `LlmDrafter.draft({ format, skill, difficulty, count, topic })` with the topic **delimited as data** (same convention as `LlmGrader`); validates the structured output with zod (`DraftedItem[]`); runs checks — duplicate (normalised-text SHA-256 equal to an existing org version, or word-5-shingle Jaccard ≥ 0.8 against the same skill's approved items, capped at 2,000 comparisons), readability (stem 20–1,200 chars; options 1–200 chars; no option equal to the stem; Flesch reading ease ≥ 30 for English), and **no candidate-facing placeholders** (`{{`); inserts passing drafts as `origin = 'ai_draft'`, `status = 'in_review'`, `ai_draft_job_id`; check results go to the job row counters and an audit row `item.ai_drafted {item_version_id, ai_draft_job_id}` per inserted draft (ids only; the check counts go to the job row and `ai_draft.complete {ai_draft_job_id, drafts_created}`; text fixed in BUILD Wave 0 to match migration M1-a, contracts spec review SPEC-C-8); failed drafts are discarded and counted. The approver sees the draft badge "AI draft — needs approval". Idempotency: key `${jobId}:ai_draft` in `idempotency_keys` (scope `ai_draft`, `trace_authoring_worker` policy). `MockLlmDrafter` returns deterministic, clearly synthetic items from `(skill, difficulty, seed)`; the production guard pattern of `messaging.ts` applies (the mock refuses `production`).

### 6.5 Pools, sections, shuffle, timers, server-side delivery (ABH-10)
Authoring as §3.3. **Publish** snapshots eligible items per section, records `min_pool_ratio`, writes package v2 (api, as D1: build → R2 → guarded update with `content_sha256` → rebuild and compare). **Delivery (edge, `SessionDO`):** at section enter the DO calls `drawSection(pkgSection, items, seed)` (`packages/item-delivery`, pure): strata from `section.draw.strata` (if absent, one stratum = all items); within a stratum a seeded weighted draw without replacement, weight = 1 / (1 + the item's exposure count frozen into the package at publish) (R2-13, pending Q-M1-4); take `count`; then item order shuffled iff `shuffleItems`, options iff `shuffleOptions`; parameterised items pick `variantIndex = next() mod variants.length`. The draw result is stored in DO storage before the first item is served (a retry or a resumed device reads it, never re-draws). Section deadline = section start + `timeLimitSeconds` (+ granted extra time pro rata, M3b); the overall deadline is still the DO alarm; leaving a section (time-out or "Finish section") closes it for good; a `forward_only` section serves no position below its highest served one, serves the next one only once the DO's accepted high-water mark reaches the request's `afterSeq` (else 409 `out_of_order` with `ackSeq`, R5-45), and records an answer for an earlier one as refused (R5-20); section states follow §4.6. Items are served one at a time as in D1. **Images:** `GET /v1/session/media/:hash` at the edge (R5-10; the candidate app shows the bytes as a `data:` URL) (session token required; the session id comes from its claims, R2-17) returns the R2 object only if the hash is in the media list of an item currently served to that session (DO check), `cache-control: no-store`, `content-type` from the stored extension.
