## 1. Scope and lead decisions
### 1.1 The slice (exit gate, build-order.md:37)
A recruiter creates a test (written + MCQ) and invites a candidate by link. The candidate takes it in the browser with a server-held timer, a start photo and autosave. The result shows **Answer Quality** (0–100, mock grader) and the **Integrity band with an evidence timeline as two separate results**. A reviewer opens the report. It is deployed on staging (`*.workers.dev` / Pages), with synthetic data only. **Exit gate:** the full flow passes an automated E2E test on staging, plus a 5-minute screen recording.

## 3. Data model (migrations are lead-only)

Conventions are build-notes §4 and `specs/m0b-tenancy.md` §3 unchanged: `org_id uuid not null` + `unique (org_id, id)` + a first-column `org_id` index (MT-2); composite FKs `(org_id, x_id)`; RLS on; one policy per operation and role set (MT-11), never `FOR ALL`, never `PUBLIC`; explicit grants, none to `anon`; invariants in triggers/CHECKs; timestamps `timestamptz not null default now()`; length CHECKs on every text column; no column name matching MT-3 (`dob`, `birth`, `honesty`, `trust_score`, `cheat`, `emotion`, `voiceprint`, `face_template`, `gaze_flag`; `reject` is banned in `integrity`, and D1 also avoids it everywhere, see I-2). Postgres is reached by `authenticated` (recruiter app, PostgREST; `services/api` org endpoints pass the user's JWT through, so RLS decides), by server workers and by `services/api`'s own role `trace_api` through `SET LOCAL ROLE` (ADR-029). **The candidate never reaches Postgres in D1 (D1-3):** `trace_candidate` and `anon` hold nothing; the api acts for the candidate through `trace_api` (§3.3). Everything below is *synthetic-only* (D1-1).

PostgREST exposes only `public` (`supabase/config.toml` `[api] schemas`), and MT-7 forbids SECURITY DEFINER outside `private`. So a **user-facing privileged step is a guarded table write** (BEFORE trigger, as in M0b), not an RPC; **worker- and api-facing steps are `private` functions** called over SQL after `SET LOCAL ROLE`. **Roles:** NOLOGIN `trace_worker`, `trace_quality_worker`, `trace_integrity_worker` (R-6) and `trace_api` (migration 2, `create role … if not exists`, M0b §2.3). MT-14 (a) forbids `rolcanlogin` on any `trace_*` role, so each is entered from an operator-created **named** login role that is not `trace_*`: `api_login` → `trace_api`, `jobs_mirror_login` → `trace_worker`, `jobs_quality_login` → `trace_quality_worker`, `jobs_integrity_login` → `trace_integrity_worker`, each `grant <role> to <login> with inherit false, set true` (so MT-14 `login_dml` stays silent, L-29); passwords are never in a migration. `scripts/ops/staging-worker-secrets.mjs` creates the four logins on staging (create-or-alter, with a SCRAM-SHA-256 verifier computed locally so the plain password never reaches a server log), grants each login its one role with `with inherit false, set true`, sets the login's server-side timeouts (`statement_timeout` 15s, `lock_timeout` 10s, `idle_in_transaction_session_timeout` 30s; revision 4o, database review Minor 1: `SET LOCAL ROLE` does not apply the target role's settings, and a stuck transaction must not hold a Hyperdrive origin slot), and refuses (TR001) a missing `trace_*` role or (TR002) any other membership or attribute; see §7.1. No login role is a member of two `trace_*` roles (MT-14 (f)). **Secrets (L-10, revision 4o):** `services/api` holds `CANDIDATE_TOKEN_PRIVATE_JWK` and `MEDIA_LINK_HMAC_KEY` (the Supabase URL and publishable key are vars); `workers/jobs` and the edge hold none. On staging each login is a Hyperdrive config (`trace-staging-<login>`, one per login so MT-14 holds, caching disabled, origin verified against the uploaded Supabase CA; ADR-031 amendment 1) reached through a binding: api `API_DB`; jobs `JOBS_MIRROR_DB`, `JOBS_QUALITY_DB`, `JOBS_INTEGRITY_DB`. `API_DB_URL` and the three `JOBS_*_DB_URL` exist only locally and are accepted only on a loopback host with no query. The `check-staging-secrets` allow-list is in §7.1.

## 10-DB. Database edge cases
| Case | Behaviour |
| --- | --- |
| Two recruiters publish the same draft at once | `for no key update` on the `tests` row serialises; the second sees `status='published'` and the guard refuses (`TRACE_GUARD`); one `test.publish` audit row and one creator assignment (`on conflict do nothing`) |
| Publish without a cutoff, or edit after publish, or change the cutoff | `quality_cutoff` is `not null` with no DB default, so a draft without one cannot exist and publish cannot lack one (L-15). After publish all child freeze triggers refuse for every role including workers and replica mode, and the cutoff is part of the frozen version row; the recruiter creates a new draft (one open draft per test); existing invitations keep their pinned version and cutoff |
| Publish or retire with the L-30 policy | the UPDATE policy's USING admits `draft`/`published` rows and its WITH CHECK carries the role arm only; the guard trigger is the only state-machine check, so draft → published and published → retired succeed, a retired row is not updatable |
| Re-publish / retire while invitations exist | retiring leaves pinned invitations valid (the DO holds the package); new invitations may pin only `published` |
| New draft version | the L-8 trigger inserts its own `ruleset_versions` row and sets both ids; a client-supplied id is overwritten; if the org has no seeded band rule version the insert fails closed |
| Two invitations created in parallel | the label trigger locks the `tests` row, so labels are gap-tolerant but unique (`Candidate n`); a rollback may leave a gap, never a duplicate |
| Duplicate `link_token_hash` (collision or replay of an insert) | global unique violation `23505`; the API retries with a new token; no row |
| `trace_api` runs without `api_org_id` (a bug), or with another org's | RLS returns no rows / refuses writes; the token-hash lookup is the only cross-org read and returns one invitation by an unguessable hash |
| Consent replayed (double click, retry) | `unique (org_id, invitation_id, event)`: `on conflict do nothing`, the api re-reads the same row and the same `session_id`; a second `session_id` write is refused (set-once) |
| Consent attempted before OTP or age, or on a blocked invitation | the consent guard refuses; no row, so no `session_id`, no `started`, no session (Q36, rule 9) |
| `SessionDO.start` fails, or `sessionStarted` is retried | the invitation stays `otp_verified` until `sessionStarted` lands (L-12); a retry finds `started` with the stored `started_at` and returns it unchanged; the DO's deadline alarm always auto-submits and mirrors, so every `started` invitation produces a `sessions` row. A consented invitation that never starts has no terminal state in D1 (accepted; M3a adds expiry after consent) |
| Invitation expires, or is revoked, near start | `expired` is allowed only while `session_id is null` (L-32); a started invitation never expires. `authenticated` may revoke only from `created|sent`, so a revoke cannot land after OTP. If a revoke wins before the OTP but the DO already started, `mirror_session` finds `revoked` (terminal), stores nothing and returns `'dead_invitation'` for a dead letter and an operator look (R-14) |
| Mirror lost or a stage never ran | the DO wrote `mirror.json` to R2 at submit; `sweep_pending` lists the session by stage and the jobs cron re-enqueues it; the idempotency key `session:job:ruleset` and the natural unique keys make a re-run safe (L-18) |
| Duplicate / replayed / reordered mirror messages | the existing `session:session_mirror:ruleset` key or `mirror_seq` ≤ stored → `'duplicate'`, no writes; a partial retry is safe by the natural unique keys; `mirror_seq` is 1 in D1 (L-6) |
| A worker writes another stage's idempotency scope | the `idempotency_keys` policy binds `scope` to the role's own job and `org_id` to `job_org_id()`; the insert is refused (L-20) |
| Paste after a page reload in the same session | signals are keyed by session-global `gseq`, so the second stream's events do not collide with the first's (L-14) |
| Mirror arrives before the media row, or the photo upload fails | the start photo uploads through the edge Worker to R2 first; `media_objects` is written only by the mirror and only for an R2 object whose key the message names. A partial or abandoned upload leaves an orphan R2 object with no row (swept by M7); a session may mirror with no photo row only if the message says `photo_missing` (camera declined or skipped, R-11), and the report shows "no start photo" (never a failure) |
| Clock skew | the DB never compares DO times with `now()` (except `sweep_pending`'s age threshold): CHECKs order only DO-supplied times (`submitted_at ≥ started_at`, `server_deadline_at > started_at`, `invitations.started_at` copied from the DO). `created_at` is DB time and is never used for the deadline. The DO's alarm and +60 s grace live in the runtime spec |
| Submit after the deadline | stored as `auto_submitted` / `submit_kind='deadline'` exactly as the DO says; the DB does not re-derive it |
| Concurrent grading and integrity jobs for one session | independent: separate schemas, roles, login roles and natural unique keys `(org_id, session_id, scoring_version)` / `(org_id, session_id, ruleset_version_id)`; a re-run is `ON CONFLICT DO NOTHING`, never an update |
| Integrity job arrives before the quality card | the job has no `shortlisted` message field: it inserts the result and an `awaiting_quality` card, finds no `quality_cards` row and retries; flags (refused by the flag trigger until the quality card exists) and the single flip wait for `meets_cutoff`. If the quality job dead-letters the card stays `awaiting_quality`, invisible to org roles, and the UI shows "Pending". If the quality card already exists, the card is inserted directly in its final state (L-4) |
| Below-cutoff session | flags inserted `not_used`, no timeline entries, card `not_reviewed_below_cutoff` (the guard requires `meets_cutoff = false` and every flag `not_used`, L-28); org roles read only `quality_cards`, so the band cannot leak through PostgREST (rule 6). `meets_cutoff` is never null (L-15) |
| Forbidden card state (for example `reviewed` with `meets_cutoff = false`) | the card guard raises on INSERT and UPDATE; no row lands |
| Report attached twice or out of order | `reports_set_once` accepts each FK column once, in either order, from its own worker only; a second attach or a change is refused; the composite FKs refuse a card of another session |
| Media link replayed, or the viewer loses access between issue and fetch | the api burns the `jti` in its DO on first fetch (a second fetch never reaches Postgres); `media_view_grant` re-checks membership, `aal`/`amr` and assignment on the one fetch, so a removed or unassigned viewer gets no key and no `media.view` row; each audit row names the viewer (L-26) |
| Org suspended mid-run | worker policies only bind `job_org_id()`; the recruiter-facing policies already hide a suspended org (M0b); a mirrored session still lands |

## 4. Candidate runtime

Scope: everything between the invite link and the receipt. The recruiter side (tests, invitations, the demo outbox) is §3 and §6; the jobs that read a submitted session are §5. ### 4.1 Flow and state machines

**Invitation states** (`invitations.status`; there is no `rejected`):

| From | To | Written by | Trigger |

Sticky and terminal. ### 4.2 Endpoints and bindings

**Common rules (edge).** JSON in and out; `Authorization: Bearer <jwt>` (no cookies); every answer carries `cache-control: no-store`; errors are `{ "error": "<code>" }` with a constant code (Hono `HTTPException` with a literal message). ### 4.3 Candidate tokens (D1-3, ADR-030)

Compact JWS, header `{alg:'ES256', typ:'JWT', kid}`; claims exactly ADR-030 §7: `{sub, candidate_id, invitation_id, org_id, typ, nonce, iat, exp}` (zod strict, `sub === candidate_id`, integer times, `nonce` ≥ 16 chars). `candidate_id` is the random v4 uuid stored on the invitation (R-10).

| `typ` | Minted by | Lifetime (`exp - iat`) | Valid on | Replay control |
| --- | --- | --- | --- | --- |
| `lobby` | api `lobbyMint` | 30 min (inference), cap 1800 s | `/v1/lobby/*`, `/v1/session/start` | the edge generates a nonce at each OTP verify and stores its hash in `InviteOtpDO`; the edge compares it on every lobby request before the RPC, so a new login kills the old lobby token. Cleared when a session token is granted |
| `session` | api `sessionGrant` | `durationSeconds + 3600`, cap 10 800 s (the grant precedes the DO's `started_at`, so the lifetime is counted from `iat`; always at least `started_at + duration + 3600 − iat`); not re-issued in D1 (no deadline moves; deviates from ADR-030's "DO asks the issuer", a simplification) | `/v1/session/*` | `nonce` hash held by `SessionDO`, compared on every request, rotated at each `sessionGrant` (one active device, Q41), moved to a read-only slot on submit (receipt only, rev 4e). **Verification at the edge**, rejecting 401 on the first failure: `alg` equals `ES256` (anything else, including `none`, before the signature); `kid` in `CANDIDATE_TOKEN_PUBLIC_JWK` (unknown → reject); signature via Web Crypto; strict claim shape; `typ` equals the route's; lifetime cap; `exp > now` and `iat <= now + 60 s`; nonce hash check (`InviteOtpDO` for `lobby`, `SessionDO` for `session`). The DO id and every id used downstream come from verified claims, never from the URL or body. `kid` form `d1-YYYY-MM`; the var holds the previous key for at least the 3 h session cap during rotation; only the current `kid` signs. **`CANDIDATE_TOKEN_PUBLIC_JWK` has one shape: a JSON array of one or two public JWKs `{kty:'EC', crv:'P-256', x, y, kid, alg:'ES256', use:'sig'}`, the signing key (`CANDIDATE_TOKEN_KID`) first**; the deploy guard (`scripts/check-deploy-vars.mjs`) and the api/edge parsers accept only that shape (lead, 2026-10-16). The key pair is generated by `scripts/ops/candidate-token-key.mjs` (lead; `scripts/ops/README.md`), which writes the private JWK for the api secret `CANDIDATE_TOKEN_PRIVATE_JWK` and the public array (with `--previous-public` for rotation). The raw link token is 32 random bytes, base64url, in the URL **fragment** (`/i#<token>`), cleared by the app with `history.replaceState`; only `sha256(token)` is stored (`invitations.link_token_hash`), looked up by api.

### 4.4 `SessionDO` protocol

**Test package** (read from R2 once at start). `packages/{test_version_id}.json` in `trace-packages-<env>`, written by api at publish, immutable, verified against `packageSha256` from the grant, ≤ 256 KB, strict `TestPackage` schema: `{v:1, testVersionId, rulesetVersionId, title, language:'en', durationSeconds, pasteBlocked:true, heartbeatSeconds:10, signalCatalogVersion, sections[{id, title, position}], items[{position, sectionId, itemVersionId, kind:'mcq'\|'written', prompt, options?[{id, label}], maxChars?}]}`. **No answer key, rubric, weight, cutoff or score field exists in the schema.** The DO copies the package into its storage and then reads R2 only to write evidence at submit.

**Storage (SQLite).** `meta` (session/org/invitation/test/ruleset/consent ids, state, `started_at`, `deadline_at`, `submit_kind`, `nonce_hash`, `active_stream_id`, `gseq_hw`, `photo`, `receipt_ref`, `mirror_state`, `mirror_attempts`); `served(position, served_at)`; `streams(stream_id, hw, opened_at)`; `events(gseq, stream_id, seq, kind, t_client, t_server, payload)` with primary key `gseq` and unique `(stream_id, seq)`; `answers(position, text|choice)`. The `session_id` is the one minted by api at consent (R-10); the DO does not mint it.

**Event numbering (L-14).** Each stream has its own client `seq` (from 1, contiguous, restarting at every start or attach). The `SessionDO` assigns a session-global **`gseq`** (from 1, contiguous across streams, in arrival order) to every event it accepts. `(stream_id, seq)` is used only for client dedupe and the ack; **`gseq`** is the number in `events.ndjson`, `integrity.signals.seq`, `SignalEvent.seq`, `Flag.signalSeqs`, the mirror's `lastEventSeq` and the answer replay order. So a paste after a reload (seq 1 again on a new stream) never collides with an earlier event and is never dropped. `gseq` is contiguous in the DO, but `events.ndjson` skips the values taken by `answer.*` events (it holds signal and heartbeat events only, L-21).

**Timer (the DO is the clock authority).** On the first `start` the DO sets `started_at` from its own clock and stores it (later calls return the stored value); `deadline_at = started_at + durationSeconds`. `sessionStarted` copies `started_at` to the invitation (set-once, §4.1). All times are server times; client `t` values are monotonic offsets kept as T3 context. One alarm at `deadline_at + 60 s` (grace for in-flight saves, plan §12). Events are accepted while `t_server <= deadline_at + 60 s` and the stream's sequence is unbroken; later ones answer 410 `closed`. At the alarm, if `in_progress`, finalise as `auto_submitted` (idempotent) and mirror. The single alarm slot is reused for mirror retries (next alarm = the earlier of the deadline alarm while in progress and the next mirror retry).

**Start / attach.** `start(grant, photo)`: if a session exists, rotate `nonce_hash` and open a new stream (resume, same `started_at`); else create it (`in_progress`) from the package. Rejects `closed` only when no session exists and a new one would start past `deadline_at + 60 s` (an existing one is auto-submitted and answers its receipt, rev 4e), and refuses unless the grant says `adultConfirmed: true` (D1-12; the DB CHECK is the second gate). `stream_id` is issued by the DO; each start/attach supersedes the previous stream (its events answer 401 `superseded`).

**Events.** One ordered stream per `(session_id, stream_id)`, `seq` from 1, contiguous. `ClientEvent` is a strict union on `kind`:

| `kind` | Payload | Meaning |
| --- | --- | --- |
| `answer.text` | `{item, p, d, i}` | splice on the item's text: keep `p` UTF-16 units, delete `d`, insert `i` (≤ 10 000), derived from the common prefix/suffix of consecutive textarea values, with both boundaries moved out of any surrogate pair so `i` and the rebuilt text are storable (rev 4h; an unstorable `i` or rebuilt text is 400). `maxChars` is enforced on the rebuilt length |
| `answer.choice` | `{item, option\|null}` | selected MCQ option, `null` clears |
| `signal` | a §4.6 shape | client-reported browser fact |
| `heartbeat` | `{}` | liveness, every 10 s |

A batch runs in one `transactionSync`: `seq <= hw` is ignored (idempotent resend, no new `gseq`); the next must be `hw + 1`; the first gap stops the batch with 409 `out_of_order` and `ackSeq = hw`; each accepted event takes the next `gseq`. Rebuild: at submit the DO replays **all** accepted `answer.*` events from empty in `gseq` order (arrival order across streams) and compares with the incremental state (D1 sends no client answer hash: `SubmitReq` is `{streamId, finalSeq}`, lead, Wave 0 contracts); the replay is the final answer. A mismatch is recorded as `replay: 'mismatch'` context (not a band input). Every 25th `answer.text` event carries `len` for an early check.

**Coverage and gaps.** The session is cut into 10 s windows from `started_at` to submit. A window is *covered* if any accepted event (heartbeat included) has `t_server` inside it, or lies inside a `tab_hidden` interval (hidden tabs throttle timers; inference). The DO reports `coverage {activeMs, coveredMs}`. A run of ≥ 3 consecutive uncovered windows is a gap `{from, to}` labelled `connectivity`, never focus loss. The band engine owns the floor (D1-6).

**Submit.** `submit(streamId, finalSeq)`: requires the stream's `hw >= finalSeq` (else 409); rebuilds answers; closes the open hidden interval; computes coverage; writes to `EVIDENCE`, in this order, `sessions/{org}/{session}/final.json` (final answers), `sessions/{org}/{session}/events.ndjson` and `sessions/{org}/{session}/mirror.json` (the mirror message below, so any stage can rebuild its input, L-18). **`events.ndjson` holds only `signal` and `heartbeat` events, one line each with `gseq`, kind, times and the §4.6 payload; no `answer.*` kind and no text field ever appears in it (L-21).** Answer edits stay in the DO, and the final answers live in `final.json` and the mirror's hash. (Rev 4e: the state is frozen and the receipt answered first; the writes and the send follow inline and then from the alarm.) It then sets `state`, moves `nonce_hash` to the read-only slot; derives `receiptRef` = first 8 Crockford-base32 chars of sha256(session_id) (deterministic; the UI shows it as `TR-XXXXXXXX`; unique per org in the DB, a collision fails the mirror loudly); stores the mirror message in `meta`; answers `Receipt {receiptRef, submittedAt}`. A repeat returns the same receipt. The receipt does not wait for Postgres.

**The one mirror message** (`SessionMirrorMessage`, strict, ≤ 100 KB; content stays in R2; **the single contract and the single queue**; the same JSON is written to `mirror.json`):

```ts

After 5 failures the message goes to the DLQ; `mirror_state` never reads "acked" unless the queue accepted the message.

### 4.5 Start photo (D1-5, rule 8)

- **Device.** After the consent row exists (§4.7), `getUserMedia({video: {facingMode: 'user', width: {ideal: 640}, height: {ideal: 480}}, audio: false})` feeds an offscreen `<video>`. A visible `<canvas>` (no `<video>` on screen, no `blob:` URL) renders each frame through the pure function `blurOutsideOval(frame, oval)` in `src/photo/blur.ts`, which works on `ImageData`-shaped pixel arrays (a down-scale/up-scale plus box blur, no `ctx.filter`, so one deterministic code path in every browser and in tests). The oval is centre 50%/50%, radii 30% of width x 42% of height. The capture canvas is the same canvas, so a pixel outside the oval is never sharp in any buffer that is uploaded. "Take photo" exports `canvas.toBlob('image/jpeg', 0.85)` at ≤ 640x480, shows it with **Retake / Use this photo**, and calls `track.stop()` on every track as soon as the shot is taken or the step is left. The oval is an `aria-hidden` SVG overlay; the instruction is text.
- **AT-D9 pixel test:** `apps/candidate/src/photo/blur.test.ts` (Vitest, node, plain pixel arrays) feeds a checkerboard frame and asserts: every pixel outside the oval has mean absolute neighbour difference < 10% of the source's; every pixel inside the oval equals the source exactly; the output size and oval geometry match; and a wrong-size input throws.
- **Never leaves the device:** the stream and every frame, the unblurred frame, face data (D1 runs no face model), audio (never requested), screen content. Only the processed JPEG is sent.
- **Upload.** `PUT /v1/lobby/photo`, body ≤ 512 000 bytes, `X-Photo-Sha256` = hex SHA-256. Edge: verifies the lobby token; calls `photoPermit` (needs the consent row; `locked` once started); rejects non-JPEG (magic `FF D8 FF`, 415), over the cap (413), dimensions outside 160-1280 px per side (415) and a hash mismatch (400); stores `EVIDENCE.put('media/{org}/{session}/start_photo.upload.jpg', body, {httpMetadata:{contentType:'image/jpeg'}, customMetadata:{sha256, blurred:'1', n}})`. This is the **working key** (rev 4e); the upload route never writes the canonical `start_photo.jpg`. The key is deterministic, so a retake overwrites (max 3). No Postgres write.
- **Upload hardening (revision 4d, C1a reviews).** Every byte check runs before `photoPermit`. Only APP0 is allowed among the APPn segments (no EXIF, thumbnail or COM) and the body must end `FF D9`. The 3 uploads are counted atomically in `InviteOtpDO`; a failed R2 put gives its slot back; the 4th upload is 429 `rate_limited` **without** `Retry-After` (the cap is permanent for the session). The permit's `orgId` must equal the token's `org_id` (else 503).
- **Record.** At `session/start` the edge first calls `InviteOtpDO.closePhotos()` (set-once; any later or in-flight upload is 410 `closed`), then `get`s the working key (missing → 403 `step_required`), checks the size and that the SHA-256 of the bytes equals the declared hash and `customMetadata.sha256` (else 400, the DO is not called), and passes `{key: canonical start_photo.jpg, sha256, bytes}` to the DO, which stores the photo hash once, at creation (a resume ignores a new photo), and puts it in the mirror. Only when the DO's stored hash equals the checked bytes' hash does the edge put those bytes to the canonical key (idempotent; a failed put is 503 with no token and no `sessionStarted`, and a retried start repeats it); then `sessionStarted`, the lobby nonce is cleared and the working key deleted (best effort) (rev 4e, SEC-1 residual); the mirror stage writes `media_objects` (`kind = 'start_photo'`, `blurred_on_device = true` is client-asserted, T3, R-18; `workspace_id` and `test_id` are copied by trigger, L-27).
- **Reviewer view (R-13, R-15, L-2, L-25, L-26).** Rule 8: 5-minute signed link, viewer watermark, every view audited, **evidence needs an assignment for every role** (the test's creator is auto-assigned). The grant functions are the §3.4 **pair**, both EXECUTE to `trace_api` only, and both take the viewer's id plus the `aal` and `amr` that api verified from the Supabase JWT (the `trace_api` connection has no `auth.jwt()`). (1) `POST /v1/orgs/:orgId/reports/:reportId/start-photo-link` (§6.2): api reads `media_objects.id` of the report's `start_photo` under the §3.3 column grant, picks a `jti` = `crypto.randomUUID()` (v4, 122 random bits; stored as `link_id`, DB review m4 m-4), and calls `private.media_link_grant(p_media_id, p_viewer, p_aal, p_amr, p_link_id)` as `trace_api`. It checks active membership, role, aal (via `membership_counts_for`) and **assignment**, and writes audit **`media.link_issued`** with the viewer as actor (`actor_kind = 'org_user'`, `actor_user_id = p_viewer`, roles from memberships). Only then api stores `{mediaId, orgId, viewerUserId, aal, amr, exp <= now + 300 s, state:'open'}` in `MediaLinkDO` and returns `{url, expiresAt, watermark:{viewerRole, org, issuedAt}}`, `url = <api origin>/media/{jti}?exp=…&sig=…` (absolute, as §6.2) with `sig = HMAC-SHA256(MEDIA_LINK_HMAC_KEY, jti|exp)`. (2) `GET /media/:jti` (the only media route, one secret): verifies `sig` (constant time) and `exp`, then `MediaLinkDO.burn(jti)` atomically (**single use**: the second fetch is 404 and never reaches Postgres), re-runs `private.media_view_grant(p_media_id, p_viewer, p_aal, p_amr, p_link_id)` for the stored viewer with the stored `aal`/`amr`, which re-checks membership and assignment and writes audit **`media.view` per fetch** (same actor rule) and only then returns the R2 key; no audit row, no bytes (fail closed). Response `cache-control: no-store`, `content-type: image/jpeg`. The viewer fetches the bytes and draws them to a canvas with a tiled overlay of the viewer's role, org and time (no bare `<img>`; a server-baked watermark is M6). Neither link nor key is logged. Tests: AT-D10 (pgTAP also asserts `actor_user_id = viewer` on both audit rows, and an aal1 recruiter with OTP allowed, with a password denied).

## 5. Results (mirror, Answer Quality, Integrity band, report)

Rule 1 shape: **three jobs, two result writers, one pointer row.** The mirror writes public session facts; `quality/score` and `integrity/band` each read only what they need and write only their own internal schema plus their own public card; `public.reports` holds one FK per card, each set by its own role. No job, view, function or trigger reads both results (D1-9, R-1, MT-5d, MT-14 (f)).

### 5.1 Jobs in `workers/jobs`

**One queue, one message, three stages.** The producer is `SessionDO`; the queue is `trace-session-mirror-<env>` with `max_retries` 5 and DLQ `trace-session-mirror-dlq-<env>` (D1-4; fallback transport in §4.4). The single `queue(batch, env)` handler validates the `SessionMirrorMessage` and `queue/consumer.ts` runs, per message: **mirror → quality → integrity**. Each stage is its own transaction on its own connection and is idempotent under the key **`${sessionId}:${job}:${rulesetVersionId}`** (session + job + ruleset, L-6) in `public.idempotency_keys`, with `job` ∈ `session_mirror`, `quality_score`, `integrity_band` (L-20). If the mirror stage fails, nothing else runs. If quality fails, integrity still runs (it finds no quality card, see below) and the message is thrown for retry after all stages were tried; a retry re-runs only what is missing. **Cutoff and `not_used` (D1-10, rule 6).** The cutoff is **mandatory and pinned in the published test version** (`test_versions.quality_cutoff int not null check (0..100)`, required to publish, editor default 40, L-15); there is no cutoff endpoint and no re-projection. The quality stage stores `meets_cutoff = (score >= cutoff)` on the quality card; it is never null. The integrity stage always computes and stores the signals, the result and the band (a band is never null). Then, using only `meets_cutoff` (L-3, L-4, L-28):
- **Quality card exists, `meets_cutoff = true`:** insert the flags as `pending`, then insert the card directly in its final state `reviewed`, then write the timeline entries (flag `state` `pending`).
- **Quality card exists, `meets_cutoff = false`:** insert every flag as **`not_used`** (on `integrity.flags` only), then insert the card as `not_reviewed_below_cutoff`. **No timeline entries are written** below the cutoff (R-2: omitted). `integrity_timeline_entries.flag_state` is `pending` only in D1; `not_used` lives on `integrity.flags`.
- **No quality card yet:** insert the card as `awaiting_quality` with **no flags and no timeline entries**. A later run (retry, or the sweep after a late quality card) inserts the flags (and, if `reviewed`, the timeline entries) and then performs exactly **one** `UPDATE` of the card to a final state. The `integrity_band` idempotency key is inserted in the same transaction as the card's final state, never at the `awaiting_quality` insert; a guard error because the quality card landed between the check and the insert is treated as a retry.

**Transactions and retries (lead, DB review m3 m-6, n-4, n-6; binding for stream R2).**
- **One transaction per stage outcome (m-6).** Quality: `grader_runs`, `scores`, the quality card, `reports.quality_card_id` and the `quality_score` idempotency key commit together. Integrity, final outcome: signals, result, flags, the card (direct final insert or the single flip), the timeline entries, `reports.integrity_card_id` (only for `reviewed`; the rule-6 attach guard refuses any other state, so a below-cutoff report keeps it null) and the `integrity_band` key commit together. Integrity, `awaiting_quality` outcome: signals, result and the card commit together, with no flag, timeline entry, pointer or key. So a card never exists without the pointer its state allows, and `sweep_pending` keeps reading cards only (no "card exists, pointer null" condition).
- **Retry after `awaiting_quality` (n-6).** The card guard runs before `ON CONFLICT`, so re-inserting an `awaiting_quality` card after the quality card has landed raises. On every run the integrity stage first reads its existing card for `(session_id, ruleset_version_id)`: none → the paths above; `awaiting_quality` and a quality card now exists → insert the flags in the state `meets_cutoff` requires, then do the single `UPDATE` (plus timeline, pointer and key in the same transaction); final → skip. It never re-inserts a card.
- **One canonicalisation for rubric hashes (n-4).** `rubric_versions.content_sha256` is opaque to the job: the job copies the stored value and never recomputes it (migration 3 seeds it as SHA-256 of `criteria::text`). `rubric_set_sha256` = SHA-256 of `canonicalJson` (sorted keys, no whitespace, the §5.2 algorithm) of the array of the used rubric versions' `content_sha256` values, sorted ascending. `quality/**` may not import `@trace/band-engine` (rule-1 wall), so the lead puts one `canonicalJson` in `@trace/shared` with the Wave-0 contracts; `band-engine` keeps its own copy for purity and a shared test vector proves the two outputs are equal.

The card guard trigger allows exactly these two paths (direct final insert, or `awaiting_quality` then one UPDATE) and enforces on INSERT and UPDATE: `reviewed` ⇔ a quality card exists with `meets_cutoff = true` and every flag `pending`; `not_reviewed_below_cutoff` ⇔ `meets_cutoff = false` and every flag `not_used`; `awaiting_quality` ⇔ no quality card and no flags. It reads only `public.quality_cards`, so the integrity job satisfies it by writing flags in the state the card will need **before** the card reaches that state. API and UI show band, flags and timeline only when `review_state = 'reviewed'`; otherwise the payload omits them ("Pending" or "Not reviewed (below cutoff)", §6.3). An integrity result never changes a quality card; the integrity job never sees a score. **Tests:** `packages/band-engine/src/input-shape.test.ts` asserts the exact key set of `BandInput` (no quality, score, cutoff or identity key; also a compile-time `expectTypeOf`); `workers/jobs/src/integrity/load.test.ts` asserts the stage's only access to quality data is `meets_cutoff` and that `integrity/**` imports no quality type; AT-D14/AT-D15 assert that publishing without a cutoff fails; pgTAP covers each forbidden card/`meets_cutoff`/flag combination.

**Sweep (L-18).** A one-minute cron in `sweep/` (neutral, `trace_worker`) calls `private.sweep_pending(p_limit)` (STABLE DEFINER, `search_path = ''`, reads only public tables, EXECUTE to `trace_worker` only), which returns `(org_id, session_id, ruleset_version_id, stage)` exactly as §3.4 defines it: `session_mirror` (invitation `started`, deadline plus grace long past, no `sessions` row), `quality_score` (session without a quality card) and `integrity_band` (session without an integrity card, or one still `awaiting_quality` while the quality card exists). ### 5.2 `packages/band-engine` (pure TypeScript)

No I/O, no clock, no randomness, **no imports at all**: the rule-table validator is hand-written, not zod. Exports (names are binding; shapes may gain optional fields in BUILD):
```ts
export const BAND_ENGINE_VERSION: string;                         // 'band-engine-1'
export type Tier = 'T1' | 'T2' | 'T3';  export type Severity = 'soft' | 'medium' | 'hard';
export type Band = 'clear' | 'review' | 'strong_concern' | 'insufficient_evidence';
export interface Rule { id: string; kinds: readonly string[]; where?: Record<string, string|number|boolean>;
  minDurationMs?: number; family: string; tier: Tier; severity: Severity; validated: boolean;
  untrusted?: boolean; rawMedia?: boolean }                       // the only two ways T3 can reach strong_concern
export interface RuleTable { version: string; coverageFloorPermille: number; coveragePhotoMissingFactorPermille: number;
  families: readonly string[]; rules: readonly Rule[] }            // the ONE rule schema; stored as jsonb in integrity.band_rule_versions
export interface SignalEvent { seq: number; atMs: number; kind: string; durationMs?: number;   // seq = the session-global gseq (L-14)
  attrs: Record<string, string|number|boolean>; mediaRef?: string }
export interface BandInput { events: readonly SignalEvent[]; coverage: { activeMs: number; coveredMs: number };
  capturedFamilies: readonly string[]; photoMissing: boolean }    // no session, candidate, org or quality field: identity-free, score-free

```
`Flag` = `{ ruleId, family, tier, severity, count, firstAtMs, signalSeqs (≤ 50, gseq values), observed }`; every flag carries timestamp, rule, observed value and evidence refs (plan §5 F). `ContextItem` = an unvalidated or unmatched signal, or a connectivity gap; shown on the timeline, never counted. `coveragePermille` is the effective value after the photo factor.

**Rule table v1** (`packages/band-engine/src/rules/d1-v1.json` is the single source; the lead's migration inserts the same JSON into `integrity.band_rule_versions.rules`; `scripts/test/band-rules-sync.test.mjs` compares the two by SHA-256 of canonical JSON). **`coverageFloorPermille = 700`, `coveragePhotoMissingFactorPermille = 750`** (both in permille everywhere; inference, calibrated in M4). `families = ['paste','input_origin','focus']`.

| Rule id | Kinds and match | Family | Tier | Severity | Validated | Effect |
| --- | --- | --- | --- | --- | --- | --- |
| `D1-PASTE` | `paste`, `drop` (**any** such event; no origin or policy attribute) | paste | T3 | medium | **true** | Review (T3 cap) |
| `D1-UNTRUSTED-INPUT` | `untrusted_input` (`isTrusted = false` key or input events) | input_origin | T3 | hard, `untrusted: true` | **true** | Strong concern (plan §6, §7.2) |
| `D1-TAB-HIDDEN` | `tab_hidden`, `minDurationMs 3000` | focus | T3 | soft | **false** | context only |
| `D1-FULLSCREEN-EXIT` | `fullscreen_exit` | focus | T3 | soft | **false** | context only |

There is no per-item paste policy and no `D1-PASTE-ALLOWED`. A paste from within the test never becomes an event (§4.6). Heartbeat gaps come in as `connectivity_gap` events derived by the integrity stage from the message's `gaps` (seq = `lastEventSeq` + 1 + index, continuing the `gseq` numbering): context, labelled "Connectivity", never `focus`. `capturedFamilies` is the catalog's family list for the message's `signalCatalogVersion` (D1: all three). D1 has no accommodation profile (M3b), so no assistive-input allow-list exists yet.

**Coverage input.** Before step 1, `coveredMs` is the DO's covered time; if `photoMissing` then `coveredMs := floor(coveredMs · coveragePhotoMissingFactorPermille / 1000)` (R-11). `coveragePermille = floor(1000 · coveredMs / activeMs)` after that. A missing photo only lowers coverage; it is recorded in `integrity_cards.photo_missing` and adds no timeline entry.

**Algorithm** (integer arithmetic only; events sorted by `(atMs, seq, kind)` first):
**Order (founder 2026-10-14, "evidence wins", R-3): flags first, coverage only blocks Clear.**
1. Only `validated` rules produce flags; a match of an unvalidated rule is `context`.
2. `strong_concern` if any flag is T1 or T2, or has `untrusted: true`, or is T3 with `rawMedia: true` and an event carrying a `mediaRef`.
3. else `review` if any T3 flag is `medium` or `hard`, or the validated T3 flags (soft or above) span **two or more distinct families**. Two soft signals in one family stay Clear (inference: the plan counts families).
4. else, if `activeMs ≤ 0` or `coveredMs · 1000 < coverageFloorPermille · activeMs` → `insufficient_evidence`, reason `low_coverage` (events stay on the timeline as context).
5. else `clear`.
`evidenceStrength = round(100 · |families ∩ capturedFamilies| / |families|) / 100`, shown beside the band (plan §7.2); a family with no capture reported counts as not usable.

**Property tests** (`packages/band-engine/src/band.property.test.ts`, fast-check; table-driven examples in `rules.test.ts`): P1 same input gives deep-equal output and identical `canonicalJson`, also after `structuredClone` and re-parse; P2 any permutation of `events` gives the same output; P3 for any generated table whose rules are all T3 without `untrusted`/`rawMedia`, the band is never `strong_concern`; P4 setting `validated = false` on any subset of rules never raises the band, and with all rules unvalidated the band is `clear` or `insufficient_evidence`; P5 coverage below the floor never gives `clear`; with no validated flag it gives `insufficient_evidence`, and a validated flag still gives `review`/`strong_concern` (evidence wins); P6 events of unmatched kinds change nothing but `context`; P7 adding a matching validated event never lowers the band rank (`clear < review < strong_concern`) at fixed coverage; P8 `evidenceStrength ∈ [0,1]` with at most 2 decimals; P9 `parseRuleTable` rejects duplicate ids, unknown keys, a floor or factor outside 1-1000 and a rule with `untrusted` or `rawMedia` on a non-T3 tier; P10 `photoMissing` never changes `flags` and never moves a band above `review`/`strong_concern` already reached: the bands with and without it differ only between `clear` and `insufficient_evidence`. D1 examples: one paste → `review`; one `untrusted_input` → `strong_concern`; 50 `tab_hidden` → `clear`; paste plus untrusted → `strong_concern`; coverage 50% with a paste → `review`; coverage 50% with no event → `insufficient_evidence`; real coverage 90% with no event and `photoMissing` (effective 675) → `insufficient_evidence`; the same with a paste → `review`; events with `seq` 1 on two streams cannot occur (the engine sees `gseq` only).

**Freeze** (D1-7, Q20): the rule table version is referenced by `ruleset_versions`, which a test version pins at publish (the draft's row is created by the L-8 trigger); update/delete of a referenced row is refused by the database (AT-D4).

### 5.4 Answer Quality computation (`workers/jobs/src/quality/`)

Inputs (as `trace_quality_worker`): the session's `responses` (rebuilt from edit events by the DO), the pinned test version's sections (weight), items, answer keys, rubric versions and `quality_cutoff`. No integrity data exists in its inputs (type level and grants).
- **MCQ item:** 100 if `selectedOptionId === correctOptionId`, else 0; unanswered 0; no negative marking. Exact key, no fuzzy match.
- **Written item:** empty scores 0 and the grader is not called; otherwise `LlmGrader.grade` (mock in D1) with the item's rubric version; `totalPercent` is the item score; every call is stored in `quality.grader_runs` (`model_id`, **`adapter_version`**, `rubric_version_id`, per-criterion points, `pass_no = 1`).
- **Section score** (hundredths, integers): `round(10000 · Σ item scores / (100 · items in section))`. Items never served (deadline auto-submit) count as 0.
- **Answer Quality** = `roundHalfUp(Σ w_s · section_s / (100 · Σ w_s))`, integer 0-100; weights are the section weights (integers ≥ 1, `Σ w > 0`). `sections.weight` is `numeric(5,2)` and the `postgres` driver returns it as a string: the job converts it to an integer and writes integer `weight` values into `quality.scores.section_scores` (`{sectionId, weight, scoreHundredths}`, the `QualityCardRow` contract), parsing that jsonb with the contract before the insert (contracts review F8).
- **Recorded:** `quality.scores` (`score`, `section_scores` with weights, `scoring_version = 'd1-scoring-v1'`, **`rubric_set_sha256`**, `rubric_version_ids`, `grader_model_id`, `grader_adapter_version`, `test_version_id`, `computed_at`; immutable) and the public `quality_cards` row with `meets_cutoff = (score >= quality_cutoff)`. The report shows these versions under the quality card only; the band engine and rule-table versions show under the integrity card only.
- Tests (AT-D15): MCQ key vectors; rounding at x.5; weights; unanswered; `meets_cutoff` boundary (score equal to the cutoff passes; `meets_cutoff` is never null; publishing without a cutoff fails); fast-check: an integer in 0-100, invariant under item order, monotone in correct MCQ answers, and **identical for the same responses whatever integrity data exists** (the function has no such parameter). **Three report payloads, three modules (L-19, rule 1).** `ReportMetaResponse` is **strict** and has exactly `report { id, label, testName, testVersion, submittedAt, receiptRefPrefix, noticeHashPrefix }` and `versions { quality: { rubricVersion, scoringVersion } \| null, integrity: { rulesetVersion } }`, from `reports`, `sessions`, `invitations` (label), `consents` (hash prefix), `test_versions` and `quality_cards`; never from an integrity card, so nothing about a below-cutoff candidate leaks. `QualityCard` = `{ state: 'pending' } \| { state: 'ready', score, sections[], graderModelId, rubricVersion, scoringVersion }`, served by `modules/report-quality/` (reads `reports`, `quality_cards` and the section names from `sections` only). `IntegrityCard` is a discriminated union on `state`: `pending {} | ready { band, evidenceStrength, coveragePct, reasons[], flags[], timeline[], signalsByFamily[], ruleTableVersion, engineVersion } | not_used_below_cutoff {}`, served by `modules/report-integrity/` (reads `reports`, `integrity_cards`, `integrity_timeline_entries` and only the boolean `quality_cards.meets_cutoff`). In `ready`, `reasons[]` and the card's one-line reason are derived by the api from `band` and the timeline entries (no column holds them). `ready` requires a visible `integrity_cards` row with `review_state = 'reviewed'` (`ruleTableVersion` is that row's `rule_table_version`); `not_used_below_cutoff` is chosen from `quality_cards.meets_cutoff = false`; everything else is `pending`. `modules/reports/` serves the metadata, the results list and the review queue (quality only; the metadata also reads `tests` for `testName`, and both lists fail closed with 503 `unavailable` past 500 reports until M2 pagination) and imports neither card module; `report-quality` and `report-integrity` import neither each other nor a shared card type (a `rule1-separation.test.ts` case). **No payload holds both a quality and an integrity value**, and the three requests carry no shared mutable state.
**Media link (R-13).** `start-photo-link`: the api reads `media_objects.id` for the report's session as the caller, calls `private.media_link_grant(…, p_viewer, p_aal, p_amr)` (membership via `membership_counts_for`, aal, **assignment**; writes audit `media.link_issued` with `actor_user_id` = the viewer and the viewer's roles, L-26; no row, no link), creates a `jti` = `crypto.randomUUID()` in `MediaLinkDO` (`{mediaId, orgId, viewerUserId, aal, amr, exp <= now + 300 s, state:'open'}`) and returns `url = <api origin>/media/{jti}?exp=…&sig=…` with `sig = HMAC-SHA-256(MEDIA_LINK_HMAC_KEY, jti|exp)` (WebCrypto). `GET /media/:jti`: verify `sig` in constant time and `exp`, **burn the `jti` atomically in `MediaLinkDO`** (a second fetch is 404 and never reaches Postgres), call `private.media_view_grant` for the stored viewer (re-checks membership, aal and assignment, writes **`media.view` per fetch** with the same actor fields, returns `r2_key`), then stream from `trace-evidence-<env>`. CORS: `ALLOWED_ORIGINS` holds the recruiter Pages origin (a plain GET with no `Authorization`; the response carries `Access-Control-Allow-Origin` for the canvas). The same variable now also governs the org routes (above).

The api must also: **(R3-1)** take `p_viewer` only from `sub` of a Supabase JWT it verified (signature, `iss`, `aud = authenticated`, `exp`, `role = authenticated`), `p_aal` only from the `aal` claim (`aal1` or `aal2`, anything else refused) and `p_amr` as the `method` strings of the `amr` objects, mapped exactly as `private.membership_counts`; never from the path, query, body or another header; the `MediaLinkDO` record stores exactly these values. **(R3-2)** run each grant in its own transaction on `API_DB_URL`: `set local role trace_api`, `trace.api_org_id` (issue: the path `:orgId` after checking the report belongs to it; fetch: the DO record's `orgId`), `trace.request_id` = a server-generated uuid (never a client header), the grant, `COMMIT`; the link is returned, or the R2 read starts, only after COMMIT succeeds. **(R3-3)** stream only the key `media_view_grant` returned, after asserting it starts with `media/${orgId}/` and ends with `/start_photo.jpg`; services/api never builds an evidence key (a static test fails on any `media/` key template outside the media read path; the key is deterministic by D1-5, so this rule, not the database, keeps "no audit row, no bytes", F1); the evidence bucket has no public `r2.dev` or custom domain and the edge has no route that reads evidence. **(R3-4)** `jti` = `crypto.randomUUID()` (v4; the audit contract's `link_id` is `z.uuid()`, DB review m4 m-4); `sig` = HMAC-SHA-256 over the versioned, domain-separated string `v1|jti|exp`; `exp` = issue time + 300 s exactly, in integer seconds (the audit row records `ttl_seconds` 300, n-2); on fetch refuse `exp < now` or `exp > now + 300`, compare `sig` in constant time, check the DO record's own `exp` too, and burn the `jti` before the DB call. **(R3-5)** every failure (bad or expired `sig`, burnt or unknown `jti`, any SQLSTATE, an R2 miss; on issue: unknown report, no photo, a denial) is the same 404 `{error:{code}}` with no detail and no echoed input. **(R3-6)** no `/media/` path or query, `jti`, `sig`, key or link id in Workers Logs, Logpush or Sentry (the recruiter `beforeBreadcrumb`/`beforeSend` drop `/media/` URLs); media responses carry `cache-control: no-store`, `Referrer-Policy: no-referrer`, `X-Content-Type-Options: nosniff`, ACAO = the exact origin with `Vary: Origin` and no credentials header, plus `Cross-Origin-Resource-Policy: same-origin` (blocks no-cors embedding; the CORS fetch still works, DC-D5); the 404 carries the same CORS, `Vary` and `no-store` headers; every method but GET gets the generic 404 before the DO (never burns); a CSP violation report or forwarded `securitypolicyviolation` event carries the full `/media/<jti>?exp=&sig=` URL in `blockedURI`, so any future `report-uri` or Sentry forwarding scrubs `/media/` too. `services/api/src/index.ts` exports only `default`, the entrypoint and the DO classes (any other export breaks `wrangler dev`, DC-D5). **(R3-7)** rate-limit link issuance per viewer. **(R3-8)** the issue endpoint filters the report and media lookup by `org_id = :orgId` (RLS alone returns rows of every org of a multi-org caller); the watermark `org` is the media's org. **(R3-9)** AT-D10 api tests: replay → 404 and no second `media.view`; expired → 404 and no row; tampered `sig` → 404; a DB denial → no bytes; an injected COMMIT failure → no bytes. **Accepted residual risk (F4, F5):** the fetch carries no `Authorization` (canvas fetch), so it re-checks membership, assignment and fence at fetch time but uses the issue-time `aal`/`amr`; a URL leaked before its first use works once, within 300 s, and the audit names the original viewer. The audit actor is asserted by the api (R-7).

### 6.3 Cutoff and `not_used` (D1-10, rule 6, ADR-006; R-2, L-3, L-15, L-28)
The cutoff is **mandatory and pinned in the published test version** (`test_versions.quality_cutoff int not null check (0..100)`): editable in the draft (default 40), immutable from publish, with **no cutoff endpoint and no re-projection**. `meets_cutoff` is therefore never null; no code path treats a missing cutoff as "everything counts". The quality job stores `meets_cutoff`; the integrity job stores `review_state` and the flags (§5.1). The card guard ties them (L-28): `reviewed` only with `meets_cutoff = true`, `not_reviewed_below_cutoff` only with `meets_cutoff = false`. `services/api/src/modules/report-integrity/projection.ts` (neutral) compares no scores: it maps what the caller can read. **API and RLS both enforce rule 6.** The api omits band, strength, flags and timeline (the keys are absent, not hidden) unless `integrity_cards.review_state = 'reviewed'`; for `meets_cutoff = false` it returns `{ state: 'not_used_below_cutoff' }`. RLS goes further: an `authenticated` policy returns only `reviewed` integrity cards and their timeline entries (§3.2), so a below-cutoff or awaiting band is unreadable through PostgREST too. If the quality card is missing, the integrity card is `pending` (never released early). Results rows show "Below cutoff" as plain text and have no action. D1 has no bulk action of any kind; bulk reject on quality cutoffs is M6. **No timeline entry is written for a below-cutoff session**; `not_used` lives on the internal `integrity.flags`, and cards and entries show flags only as `pending`.
