## 1. Scope and lead decisions
### 1.1 The slice (exit gate, build-order.md:37)
A recruiter creates a test (written + MCQ) and invites a candidate by link. The candidate takes it in the browser with a server-held timer, a start photo and autosave. The result shows **Answer Quality** (0–100, mock grader) and the **Integrity band with an evidence timeline as two separate results**. A reviewer opens the report. It is deployed on staging (`*.workers.dev` / Pages), with synthetic data only. **Exit gate:** the full flow passes an automated E2E test on staging, plus a 5-minute screen recording.

## 3. Data model (migrations are lead-only)

Conventions are build-notes §4 and `specs/m0b-tenancy.md` §3 unchanged: `org_id uuid not null` + `unique (org_id, id)` + a first-column `org_id` index (MT-2); composite FKs `(org_id, x_id)`; RLS on; one policy per operation and role set (MT-11), never `FOR ALL`, never `PUBLIC`; explicit grants, none to `anon`; invariants in triggers/CHECKs; timestamps `timestamptz not null default now()`; length CHECKs on every text column; no column name matching MT-3 (`dob`, `birth`, `honesty`, `trust_score`, `cheat`, `emotion`, `voiceprint`, `face_template`, `gaze_flag`; `reject` is banned in `integrity`, and D1 also avoids it everywhere, see I-2). Postgres is reached only by `authenticated` (recruiter app, PostgREST) and by server workers through `SET LOCAL ROLE` (ADR-029). **The candidate never reaches Postgres in D1 (D1-3):** `trace_candidate` and `anon` hold nothing. Everything below is *synthetic-only* (D1-1).

PostgREST exposes only `public` (`supabase/config.toml` `[api] schemas`), and MT-7 forbids SECURITY DEFINER outside `private`. So a **user-facing privileged step is a guarded table write** (BEFORE trigger, as in M0b), not an RPC; **worker-facing steps are `private` functions** that a worker calls over SQL after `SET LOCAL ROLE`.

### 3.2 Tables
Notation: **W** = who writes (a role, or "guard trigger"). `ws` = `workspace_id`, copied from `tests` by a BEFORE INSERT trigger on every test-descendant table and immutable (composite FK `(org_id, workspace_id) → workspaces`), so workspace-scoped recruiters (M0b D16b) are fenced on every child table. **Freeze triggers** (`F`) are SECURITY DEFINER, `ENABLE ALWAYS` (replica mode cannot skip them, as for `audit_log`), fire for workers too, and have **no operator bypass** (Q20).

**Decision: no `items` table in D1.** D1 has no pools, reuse, import or AI drafting, so item identity adds nothing. `item_versions` carries `item_id uuid not null default gen_random_uuid()` (a stable identity with no FK). M1 adds `items`, the FK, and relaxes `section_id` to nullable; no D1 column is dropped (additive).

W: `authenticated` (OW/AD/RC); `invitation_seq` is outside the column grant and is bumped only by the invitation label trigger. Guard: `workspace_id`, `created_by` immutable. Audit `test.create`.
- **`test_versions`**: `id, org_id, workspace_id, test_id, version_no int, status test_version_status (draft|published|retired), total_time_seconds int (60–14400), quality_cutoff numeric(5,2) null (0–100), ruleset_version_id, notice_version_id, content_sha256 text null (64 hex), published_at, published_by, created_by`. Unique `(org_id,test_id,version_no)`, `(org_id,id)`, `(org_id,id,ruleset_version_id)` (target of the session FK); partial unique `(org_id,test_id) where status='draft'` (one open draft). FKs composite to `tests`, `ruleset_versions`, `notice_versions`. CHECK `(status='draft') = (published_at is null)`; CHECK `status='draft' or (content_sha256 is not null and ruleset_version_id is not null and notice_version_id is not null)`. **Publish = `UPDATE … set status='published'`** (no RPC, see above). ### 3.5 Catalog-check impact (lead-only files)
- **MT-1/MT-2/MT-4/MT-9/MT-12:** all 22 tables carry RLS and an `org_id`-leading index; no `anon` privilege, no non-owner `TRUNCATE/TRIGGER/REFERENCES`; all objects owned by `postgres`; no default-ACL change.
- **MT-3:** no banned name. D1 adds a stricter *pgTAP* scan (not a catalog change): no column named like `%reject%` in any schema, and none like `%score%|%band%|%grade%|%outcome%` in `responses`, `invitations`, `sessions`, `media_objects`, `reports`.
- **MT-5a–d:** no view, function, trigger, policy, default or CHECK reaches both schemas. `reports` has FKs into both (founder-allowed `outside_host_both`); `ruleset_versions` and the worker tables reference only `public` or one schema. `mirror_session` and `media_view_grant` reach `public` only. Each worker role holds privileges in one schema only (MT-5c, MT-14 `both_schemas`). **A worker's login role must not be a member of both worker roles:** `workers/jobs` therefore uses two login roles and two connections, one per schema (OPEN-4). Login roles are created by the operator runbook, never in a migration; MT-14 `login_dml` keeps them DML-free until `SET ROLE`.
- **MT-6:** `integrity.band` and every integrity enum label avoid `reject`. `invitation_status` is in `public` and has no such label either (rule 2).
- **MT-11 (needs a lead change):** add `private.job_org_id` and `private.my_assigned_test_ids` to the caller-dependent helper allow-list (`helper_function`), each with a positive and a negative fixture. Without it every worker policy would need a literal-true clause plus an `ADR-` reference-list entry, which would also exempt the table's `authenticated` policies from MT-11 (rejected). `idempotency_keys` stays the only reference table.
- **MT-13 (recommended new check, e.g. MT-15 `append_only_registry`):** MT-13 is hard-wired to `audit_log`. D1 adds three more append-only tables (`public.consents`, `integrity.signals`, `quality.grader_runs`); a registry-driven check with MT-13's seven branches stops them drifting. Not required to pass the existing checks; floors only rise.
- **Floors:** `catalog-min-count` rises by the new fixtures (≈ +4 for MT-11, +7 if MT-15 is added). `rls-min-count` is set to the real count at the end of BUILD (§3.6 estimates ≈ 400 new, so about 1,100).

## 4. Candidate runtime

Scope: everything between the invite link and the receipt. The recruiter side (creating tests and invitations, the demo outbox) is §3; the mirror consumer's writes to `quality.*` / `integrity.*` and the report are §5–§7. Marks: "(inference)" = not stated in a decision or source, chosen here; "OPEN:" = needs the lead or founder. ### 4.1 Flow and state machines

**Invitation states** (`invitations.status`; there is no `rejected`):

| From | To | Written by | Trigger |
| --- | --- | --- | --- |
| (new) | `created` → `sent` | `services/api` (§3) | recruiter creates, then sends (mock Messaging writes the demo outbox) |
| `sent` | `otp_verified` | `services/api` | first successful `otpVerify`. Later logins (resume) leave the state alone |
| `created`, `sent`, `otp_verified` | `blocked_age` | `services/api` | `ageDeclare(adult=false)`, or the inviter's `adult_confirmed_by_inviter = false`. Sticky and terminal (a later "adult" answer is refused) |
| `otp_verified` | `started` | `services/api` | first `sessionGrant` (sets `started_at`; this is the timer origin, §4.4) |
| `started` | `submitted` | `workers/jobs` | the mirror message (§4.4) for a `submitted` or `auto_submitted` session |
| `created`, `sent`, `otp_verified`, `started` | `expired` | `services/api` | lazily, when `now > expires_at` is seen at resolve / OTP / grant. A `started` session is **not** cut short (below) |
| `created`, `sent`, `otp_verified`, `started` | `revoked` | `services/api` (§3) | recruiter action |

### 4.3 Candidate tokens (D1-3, ADR-030)

Format: compact JWS, header `{alg:'ES256', typ:'JWT', kid}`; claims exactly ADR-030 §7: `{sub, candidate_id, invitation_id, org_id, typ, nonce, iat, exp}` (zod strict object, `sub === candidate_id`, integer times, `nonce` ≥ 16 chars). D1 has no `candidates` table, so `candidate_id` is a random v4 pseudonymous uuid stored on the invitation row (OPEN: needs `invitations.candidate_id uuid default gen_random_uuid()` in §3's schema; ADR-030 requires random v4 ids).

| `typ` | Minted by | Lifetime (checked as `exp - iat`) | Valid on | Replay control |
| --- | --- | --- | --- | --- |
| `lobby` | api `otpVerify` | 30 min (inference; ADR-030 left it to this spec). Cap 1800 s | `/v1/lobby/*`, `/v1/session/start` | `nonce` hash held by `InviteOtpDO`; every OTP verify rotates it, so a new login kills the old lobby token. Cleared when a session token is granted |
| `session` | api `sessionGrant` | `started_at + durationSeconds + 3600 − iat`; cap 10 800 s. | `portal` | not minted in D1 | n/a | rejected everywhere | n/a |

**Verification at the edge**, in this order, rejecting with 401 on the first failure: header `alg` must equal `ES256` (anything else, including `none`, is rejected before the signature); `kid` looked up in `CANDIDATE_TOKEN_JWKS` (unknown → reject); signature via Web Crypto; strict claim shape; `typ` equals the route's `typ`; lifetime cap; `exp > now` and `iat <= now + 60 s` (60 s skew allowance, server clocks only); for `session`, `sha256(nonce)` equals the DO's value. The DO id and every id used downstream come from verified claims, never from the URL or body. Keys: `kid` form `d1-YYYY-MM`; the JWKS var holds the current and, during rotation, the previous key for at least the 3 h session cap; only the current `kid` signs. The private JWK is generated by an ops script (lead, `scripts/ops/`) and set as an api Worker secret. The raw link token is 32 random bytes, base64url, carried in the URL **fragment** (`/i#<token>`), so no server, log or Referer ever sees it; the app clears it with `history.replaceState` after reading (§4.7). Only `sha256(token)` is stored (`invitations.link_token_hash`).

### 4.4 `SessionDO` protocol

**Test package (read from R2 once, at start).** `packages/{test_version_id}.json`, written by api at publish, immutable, verified against `packageSha256` from the grant, ≤ 256 KB, validated with a strict `TestPackage` schema: `{v:1, testVersionId, rulesetVersionId, title, language:'en', durationSeconds, pasteBlocked:true, heartbeatSeconds:10, signalCatalogVersion, sections[{id, title, position}], items[{position, sectionId, itemVersionId, kind:'mcq'\|'written', prompt, options?[{id, label}], maxChars?}]}`. **No answer key, rubric, weight or score field exists in the schema**; keys stay in Postgres for scoring. The DO copies the package into its own storage at start and never reads Postgres or R2 again except to write evidence at submit.

**Storage (SQLite tables).** `meta` (one row: session/org/invitation/test/ruleset/consent ids, state, `started_at`, `deadline_at`, `submit_kind`, `nonce_hash`, `active_stream_id`, `photo`, `receipt_ref`, `mirror_state`, `mirror_attempts`); `served(position, served_at)`; `streams(stream_id, hw, opened_at)`; `events(stream_id, seq, kind, t_client, t_server, payload)` with primary key `(stream_id, seq)`; `answers(position, text|choice)` (the incrementally rebuilt state).

**Timer.** `started_at` is the grant's `startedAt` (set in Postgres once), `deadline_at = started_at + durationSeconds`. All times are server times; client `t` values are monotonic offsets (ms since stream open) kept as T3 context. One alarm is scheduled at `deadline_at + 60 s` (the grace for in-flight saves, plan §12). Events are accepted while `t_server <= deadline_at + 60 s` and the stream's sequence is unbroken; later ones answer 410 `closed`. At the alarm, if `in_progress`: finalise as `auto_submitted`. The alarm handler is idempotent; the single alarm slot is reused for mirror retries (next alarm = the earlier of "deadline + 60 s while in progress" and "next mirror retry while pending").

**Start / attach.** `start(grant, photo)`: if a session exists, only rotate `nonce_hash` and open a new stream (resume); otherwise create the session (`in_progress`) from the package. Rejects (`closed`) if `now > deadline_at + 60 s`. `adultConfirmed` must be `true` in the grant or the DO refuses (D1-12; the DB CHECK is the second gate on mirror). `stream_id` is issued by the DO (random uuid), never chosen by the client; each start/attach supersedes the previous stream (events from it answer 401 `superseded`).

**Events.** One ordered stream per `(session_id, stream_id)`, `seq` from 1, contiguous. `ClientEvent` is a strict discriminated union on `kind`:

| `kind` | Payload | Meaning |
| --- | --- | --- |
| `answer.text` | `{item, p, d, i}` | splice on the item's current text: keep `p` UTF-16 units, delete `d`, insert string `i` (≤ 10 000); the client derives it from the common prefix/suffix of consecutive textarea values. `maxChars` is enforced on the rebuilt length |
| `answer.choice` | `{item, option\|null}` | selected MCQ option, `null` clears |
| `signal` | one of the §4.6 shapes | client-reported browser fact |
| `heartbeat` | `{}` | liveness; sent every 10 s even when nothing else is pending |

A batch is processed in one `transactionSync`: events with `seq <= hw` are ignored (idempotent resend); the next must be `hw + 1`; the first gap stops the batch and answers 409 `out_of_order` with `ackSeq = hw` so the client resends from `hw + 1`; `hw` is the high-water mark per stream. Rebuild: at submit the DO replays **all** accepted `answer.*` events from empty, in arrival order across streams, and compares the result with the incremental `answers` state and with the SHA-256 of each answer the client sends in `SubmitReq`; the replay result is the final answer. A mismatch is recorded as `replay: 'mismatch'` context in the mirror (inference: not a band input in D1, since D1-6 lists the only inputs). Every 25th `answer.text` event carries `len` (expected resulting length) for a cheap early check.

**Coverage and gaps.** The session is cut into 10-second windows from `started_at` to the submit time. A window is *covered* if any accepted event (heartbeat included) has `t_server` inside it, or if it lies inside a `tab_hidden` interval (browsers throttle timers in hidden tabs, so hidden time must not look like a network gap; inference). `heartbeatCoverage = covered / total`. A run of ≥ 3 consecutive uncovered windows is recorded as a gap `{from, to}` labelled `connectivity` (never focus loss). Both go in the mirror; the band engine owns the floor (D1-6).

**Submit.** `submit(streamId, finalSeq)`: requires `hw >= finalSeq` for that stream (else 409 `out_of_order`); rebuilds answers; closes the open hidden interval; computes coverage; writes to R2 `EVIDENCE` the objects `sessions/{org}/{session}/final.json` (answers) and `sessions/{org}/{session}/events.ndjson` (the full event log; signal events contain no content, §4.6); sets `state` and clears `nonce_hash`; derives `receipt_ref = "TR-" + first 8 Crockford-base32 chars of sha256(session_id)` (deterministic, so a retry returns the same value; unique per org is enforced by the DB, a collision would fail the mirror loudly); stores the mirror message in `meta`; answers `SubmitRes`. Calling submit again returns the same receipt. The candidate's receipt does not wait for Postgres: the DO is the authority.

Consumer (`workers/jobs`, §5/§6 for what it fans out): validates, reads `final.json` / `events.ndjson` from R2 and verifies the hashes, then in one transaction upserts `sessions`, `session_items`, `responses`, `media_objects` (kind `start_photo`), and inserts `integrity.signals`, with `on conflict` keyed by `jobKey` / `(session_id, job_kind, ruleset_version_id)` and forward-only `mirror_seq`; marks the invitation `submitted`. A redelivered message does nothing. After 5 failures it lands in the DLQ; the DO's `mirror_state` never shows "acked" unless the queue accepted the message.

**Delivery and fallback.** `MIRROR_TRANSPORT = 'queue'`: `MIRROR_QUEUE.send(msg)` (`contentType: 'json'`). If `send` throws, `mirror_state` stays `pending` and the DO alarm retries with backoff 5 s, 15 s, 60 s, then every 5 min, for 24 h, then marks `failed` and logs `session.mirror_failed` (operator action). `MIRROR_TRANSPORT = 'service'` (if Queues are unavailable on the plan, DC-D2): the same message goes to `env.JOBS.mirror(msg)`, a `MirrorRpc` entrypoint on `workers/jobs` that runs the same consumer function directly and returns after commit; the same alarm retry applies. One consumer function, two transports; a unit test runs the same fixtures through both.

### 4.5 Start photo (D1-5, rule 8)

- **Device.** After the consent row exists (§4.7), `getUserMedia({video: {facingMode: 'user', width: {ideal: 640}, height: {ideal: 480}}, audio: false})` feeds an offscreen `<video>`. A visible `<canvas>` (the only thing shown, no `<video>` on screen, no `blob:` URL) renders each frame: draw the frame blurred (`ctx.filter = 'blur(14px)'`; where `ctx.filter` is unsupported, e.g. Safari, a down-scale to 1/12 and up-scale), then `clip()` to the **oval** (centre 50% / 50%, radii 30% of width × 42% of height) and draw the sharp frame inside it. The capture canvas is this same canvas, so a pixel outside the oval is never sharp in any buffer that is uploaded. "Take photo" exports `canvas.toBlob('image/jpeg', 0.85)` at ≤ 640×480, shows the result on the canvas with **Retake / Use this photo**, and calls `track.stop()` on every track as soon as the shot is taken or the step is left. The oval is an SVG overlay (`aria-hidden`) with the instruction as text ("Place your face inside the oval. Everything outside it is blurred on your device before upload").
- **Never leaves the device:** the video stream and every frame, the unblurred frame, any face data (D1 runs no face model), audio (never requested), screen content. Only the processed JPEG is sent.
- **Upload.** `PUT /v1/lobby/photo`, `Content-Type: image/jpeg`, body ≤ 512 000 bytes, `X-Photo-Sha256` = hex SHA-256 of the body. Edge: verifies the lobby token; calls `photoPermit` (needs consent; `locked` once started); rejects non-JPEG (magic `FF D8 FF`, 415 `bad_media`), size over the cap (413), unreadable or out-of-range dimensions (SOF header must give 160–1280 px per side, 415), and a hash mismatch (400); stores with `EVIDENCE.put('media/{org}/{session}/start_photo.jpg', body, {httpMetadata:{contentType:'image/jpeg'}, customMetadata:{sha256, blurred:'1', n}})`. The key is deterministic, so a retake overwrites (max 3). No Postgres write here.
- **Record.** At `session/start` the edge `head()`s the object, checks `sha256`, and passes `{key, sha256, bytes}` to the DO, which puts it in the mirror; the jobs consumer writes the `media_objects` row (`kind = 'start_photo'`, `blurred_on_device = true`, `retention_class = 'media'`). `blurred_on_device` is client-asserted and cannot be verified by the server (OPEN: accepted T3 limitation in D1; on-device checks and the server-requested stills are M4).
- **Reviewer view** (api, Supabase-authenticated staff; the report UI is §7). `POST /v1/media/{media_id}/view-link` (recruiter/reviewer/owner/admin who can see that report; RLS-visible `media_objects` metadata) returns `{url, expiresAt, watermark: {viewer, issuedAt}}`; `url` is `/v1/media/{media_id}?uid=…&exp=…&sig=…` on api with `sig = HMAC-SHA256(MEDIA_LINK_HMAC_KEY, media_id|uid|exp)`, `exp <= now + 300 s`. `GET` verifies `sig` (constant time) and `exp`, reads the object through the api `EVIDENCE` binding, answers with `cache-control: no-store`, `content-type: image/jpeg`, and writes `audit_log` action `media.view` (actor `uid`, object `media_id`) **per fetch**; issuing a link also writes `media.link_issued`. The viewer component fetches the bytes and draws them to a canvas with a tiled watermark of the viewer's identity and the time (no bare `<img>`). Neither the link nor the HMAC is ever logged (`signedurl` is a redacted stem anyway). OPEN: a watermark baked into the pixels needs server-side image processing (not on Workers without a new service); D1 uses the canvas overlay, which a determined viewer can bypass by saving the raw response. Rule 8 says "viewer watermark" without saying where it is applied.

### 4.6 Client signals (D1-6)

Captured in one module `signals.ts` on the test screen only. Every payload is metadata: an item position, a length, a count or a duration. **No pasted, dropped or typed text, no clipboard content, no file names** (the redactor stems `text`, `content`, `answer` cover logs; the schema covers the wire). Events are stamped `tier: 'T3'` and `validated` by the DO/jobs from a versioned constant `SIGNAL_CATALOG` in `@trace/shared`; the client sends neither.

| `sig` | Captured how | Payload | Band use (D1-6) |
| --- | --- | --- | --- |
| `paste` | capture-phase `paste` on `document`; `preventDefault()` (the package sets `pasteBlocked`); skipped if the text equals the last in-test `copy`/`cut` selection (compared in memory on the device, so pasting within the test is ignored per plan §6) | `{item, len}` | T3, caps at Review. `validated = true` for the D1 rule version |
| `drop` | capture-phase `drop` on `document`; `preventDefault()` | `{item, len, dt: 'text'\|'files'\|'other'}` | as `paste` |
| `untrusted_input` | capture-phase `keydown`, `beforeinput`, `input` where `event.isTrusted === false`; coalesced per item per 5 s | `{item, via: 'keydown'\|'beforeinput'\|'input', count}` | Strong concern (plan §6 exception) |
| `tab_hidden` | `visibilitychange` hidden → visible; ignores absences < 3 s (plan §6); `ms` from the monotonic clock | `{item, ms}` | **context only**, `validated = false` |
| `fullscreen_exit` | `fullscreenchange` with `document.fullscreenElement === null` after the test entered fullscreen on "Start test" (user gesture); not emitted at submit | `{item}` | **context only**, `validated = false` |
| heartbeat | not a signal; a `heartbeat` event every 10 s | `{}` | feeds coverage, never a flag |

`item` is the item position being shown, or `null`. Context-only signals are still shown on the evidence timeline (§7) and never change the band; the band engine reads `validated` from the rule version, not from the event. Connectivity gaps are labelled `connectivity` and never create a signal. OPEN: `untrusted_input` is Strong concern by founder decision (2026-10-14), but browser extensions (spelling and writing assistants, autofill, some IMEs and assistive tools) dispatch synthetic input events, and its precision is unmeasured; rule 3 asks for precision ≥ 90% and false-positive rate < 5% before a detector counts. The accommodation allow-list that plan §6 relies on is M3b. Mitigation available now: the report copy for this signal says what was observed ("events not produced by the keyboard"), never "cheating". No other signal is captured (no keystroke timing, no face, no focus-blur other than the above).

### 4.8 Candidate-runtime edge cases (§10-RT)

| # | Case | Behaviour |
| --- | --- | --- |
| RT-1 | Network lost mid-save | Client keeps unacknowledged events in memory (up to 10 min), shows "Offline: your answers are kept on this device until you reconnect", resends from `ackSeq + 1`. The DO's `hw` makes resends idempotent. The timer keeps running on the server; D1 credits no outage time and never pauses (Q38's pause and credit are M3a). A closed tab with unsent events loses them; acknowledged events are never lost. No encrypted IndexedDB buffer in D1 (Q40 is M3a). OPEN: confirm these three are acceptable for D1 |
| RT-2 | Gap in `seq` (a batch was lost) | 409 `out_of_order` + `ackSeq`; client resends the missing range. After the grace the DO finalises from what it has |
| RT-3 | Double tab / duplicated tab / second device | A second login or `attach` opens a new stream (and a new login rotates the nonce). The older page's next batch gets 401 `superseded`; it stops sending and shows "This test is open in another window". Resumes are counted (`resumeCount`) and are context only, never a flag (Q41) |
| RT-4 | Reload | `sessionStorage` token → `attach` → `view` restores items, answers and timer; a new `streamId` starts at seq 1. Unflushed text newer than the last ack (≤ 2 s) is lost |
| RT-5 | Deadline reached while saving or submitting | Server time decides: events received before `deadline + 60 s` and contiguous are accepted; the client flushes and submits at zero; the alarm auto-submits at `deadline + 60 s`; later batches get 410 `closed` and the UI shows the receipt via `attach`. Photo upload cannot collide with the deadline because the timer starts only at `session/start` |
| RT-6 | OTP brute force | 6 digits, 10 min, 5 attempts per challenge, then a 15-min lock (429 `otp_locked`, `Retry-After`); a new challenge invalidates the old one; max 3 resends per 10 min; limits keyed by invitation, never IP (Q47); comparison in constant time; the code is stored salted-hashed in the DO and returned only to api for the Messaging mock |
| RT-7 | Link expired or revoked | Before a session: `resolve` answers `expired`/`revoked`, no OTP is sent, no grant is made. Mid-session: the session continues to its deadline and submits (no live revoke in D1, OPEN above). After submit the link shows "already submitted" |
| RT-8 | Under 18 at either source | Inviter says under 18 → `blocked_age` before any OTP request; candidate says under 18 → `blocked_age` at step 3. No consent, session, photo or camera is created or requested; only the boolean and its source are stored (MT-3). A later "adult" answer or a second tab cannot undo it; `sessionGrant` and `SessionDO.start` both refuse |
| RT-9 | Camera denied / none / unsupported | Plain-language screen, a retry button, and "Continue without a photo". Choosing it sets `photoSkippedReason` (`camera_denied`, `no_camera`, `declined`); it is recorded as a context note on the report and is never labelled as suspicious. OPEN: plan §6 says a declined camera lowers evidence coverage, but D1's only coverage measure is heartbeat coverage and no D1 detector uses the camera, so the band is unchanged; recommend allowing the skip and keeping the note, not blocking (blocking would also fail candidates on shared lab machines) |
| RT-10 | Clock skew | Token checks use server clocks only (60 s skew on `iat`); the candidate's clock never reaches the deadline, the coverage windows or any signal time; the visible timer resyncs on every ack; a laptop sleep is corrected by the next ack |
| RT-11 | R2 or DO unavailable | `/events` answers 503 `unavailable`; the client treats it like RT-1. If `SessionDO.start` fails after `sessionGrant` marked the invitation `started`, a retry of `session/start` re-grants with the **same** `startedAt` and the DO uses it (the timer does not restart) |
| RT-12 | Test package missing or hash mismatch | `start` fails with 503; nothing is served. An operator error, logged as `session.package_invalid` with `sessionId` and `pkg` only |
| RT-13 | Oversize or malformed input | Body caps and strict schemas reject before the DO is touched; an `answer.text` that would exceed `maxChars` is rejected as a whole batch (400 `bad_request`) and the UI keeps the last good text |
| RT-14 | Browser support | Chromium and Firefox first (Q46); Safari lacking `ctx.filter` uses the down-scale blur; no `requestFullscreen` is tolerated silently (no `fullscreen_exit` is raised if it never started) |

## 5. Results (mirror, Answer Quality, Integrity band, report)

Rule 1 shape in one line: **three consumers, two result writers, one pointer row.** The mirror writes session facts; `quality/score` and `integrity/band` each read only what they need and write only their own schema; `public.reports` holds one nullable FK per card, each set by its own role. No job, view, function or trigger reads both results (D1-9, MT-5d, MT-14 (f)).

### 5.1 Jobs in `workers/jobs`

**Queues** (D1-4; names get `-staging` / `-dev`): `trace-session-mirror` (producer: `SessionDO`, in `workers/edge`), `trace-quality-score`, `trace-integrity-band` (producer: the mirror handler), one dead-letter queue each (`max_retries = 3`). One `queue(batch, env)` handler in `src/index.ts` switches on `batch.queue` (neutral code). If DC-D2 fails, D1-4's fallback replaces the producers with a service binding; the handlers below do not change.

**Folder layout** (the ESLint rule-1 test, `packages/config/test/rule1-separation.test.ts`, forbids `quality/**` and `integrity/**` from importing each other **or any neutral local file**):
```

  queue/consumer.ts         neutral wiring: opens one SQL session per job and INJECTS it
  mirror/                   trace_worker: handler.ts, schema.ts (zod MirrorMessage), writes.ts
  quality/                  trace_quality_worker: handler.ts, score.ts, mcq.ts, written.ts, store.ts

Secrets: `JOBS_MIRROR_DB_URL`, `JOBS_QUALITY_DB_URL`, `JOBS_INTEGRITY_DB_URL` (names are an inference; allow-list in §7.2).

**Idempotency** (CLAUDE.md "session + job + ruleset"; build-notes invariant 10). Every insert is `on conflict (key) do nothing` followed by a re-read, so a replay returns the same row and the same ids:

| Job | Message | Unique key | Writes (as role) |
| --- | --- | --- | --- |
| `mirror` | `MirrorMessage { v, sessionId, orgId, finalAnswers, events[], coverage, capturedFamilies, startPhotoRef, submittedAt }` | `(session_id, seq)` for events; `session_id` for the submit | `sessions`, `session_items`, `responses`, `session_events`, `media_objects`, one `reports` row (`unique (session_id)`, both card FKs null, both states `pending`) as `trace_worker`; then enqueues the two result messages **after commit** |
| `quality/score` | `{ sessionId, testVersionId }` | `quality.scores unique (session_id, rubric_set_version_id, scoring_version)`; `quality.grader_runs unique (session_id, item_id, rubric_version_id, model_id, pass_no)` | `quality.grader_runs`, `quality.scores`; then `update public.reports set quality_score_id, quality_state='ready' where session_id=$1 and quality_score_id is null` |

**How `public.reports` is filled without a code path holding both results** (D1-9, build-notes §0 "Rule 1 catalog check"): the `reports` row is created empty by the mirror. `trace_quality_worker` holds `UPDATE (quality_score_id, quality_state)` only, `trace_integrity_worker` holds `UPDATE (integrity_result_id, integrity_state)` only (column grants; neither can read the other's column set in a way that matters, neither has USAGE on the other schema). A trigger makes each FK set-once. Nothing computes "ready" in the database: **readiness is read by `services/api`** as `quality_state ≠ pending and integrity_state ≠ pending`, and the API returns the two cards as two sibling objects (§6.2). A failed job lands in its DLQ; the DLQ consumer of that side sets only its own `*_state = 'failed'`.

**Sweep** (inference): a one-minute cron in `sweep/` (neutral, `trace_worker`, reads only `public.reports`) re-enqueues the missing result message for any report older than 2 minutes with a `pending` state. Safe by the keys above. It covers a lost enqueue between mirror commit and send.

**Cutoff and `not_used`** (D1-10): neither job reads the cutoff or the other card. `integrity/band` always computes and stores band and flags (`pending`). The cutoff is applied **at read time** in `services/api` (§6.3). Integrity code therefore never sees a quality score, and quality code never sees a band.

**Time budget** (ADR-021): quality (mock grader) and band are both under 30 s p95 after submit by construction; the E2E records `time_to_ready_ms` per candidate (AT-D17). Workers Free allows 10 ms CPU per invocation; DC-D8 measures the three handlers.

export interface BandInput { events: readonly SignalEvent[]; coverage: { activeMs: number; coveredMs: number };
  capturedFamilies: readonly string[] }                           // no session, candidate or org id: identity-free
export interface BandOutput { band: Band; reasons: readonly string[]; evidenceStrength: number;  // 0..1, 2 decimals
  coveragePermille: number; flags: readonly Flag[]; context: readonly ContextItem[]; ruleTableVersion: string; engineVersion: string }
export function parseRuleTable(raw: unknown): RuleTable;          // zod, strict; rejects unknown keys and duplicate ids
export function computeBand(table: RuleTable, input: BandInput): BandOutput;
export function canonicalJson(value: unknown): string;           // sorted keys; the job hashes it (SHA-256) into integrity.results.input_hash
```
`Flag` = `{ ruleId, family, tier, severity, count, firstAtMs, signalSeqs (≤ 50), observed }`; every flag therefore carries timestamp, rule, observed value and evidence refs (plan §5 F). `ContextItem` = an unvalidated or unmatched signal, shown on the timeline, never counted.

**Rule table v1** (`packages/band-engine/src/rules/d1-v1.json` is the single source; the lead's migration inserts the same JSON into `integrity.band_rule_versions`; `scripts/test/band-rules-sync.test.mjs` compares the two by SHA-256 of canonical JSON). `coverageFloorPermille = 700` (inference; calibrated in M4). `families = ['paste','input_origin','focus']`.

| Rule id | Kinds and match | Family | Tier | Severity | Validated | Effect |
| --- | --- | --- | --- | --- | --- | --- |
| `D1-PASTE-BLOCKED` | `paste`, `drop`; `origin=external`, `policy=blocked` | paste | T3 | medium | **true** | Review |
| `D1-PASTE-ALLOWED` | `paste`, `drop`; `origin=external`, `policy=allowed` | paste | T3 | soft | **true** | one soft T3 signal: Clear alone |
| `D1-UNTRUSTED-INPUT` | `untrusted_input` (`isTrusted = false` key or input events) | input_origin | T3 | hard, `untrusted: true` | **true** | Strong concern (plan §6, §7.2) |
| `D1-TAB-HIDDEN` | `tab_hidden`, `durationMs ≥ 3000` | focus | T3 | soft | **false** | context only |
| `D1-FULLSCREEN-EXIT` | `fullscreen_exit` | focus | T3 | soft | **false** | context only |

`paste` with `origin=internal` matches no rule (plan §6: pasting from within the test is ignored) and appears as context. Heartbeat gaps come in as `connectivity_gap` events: context, labelled "Connectivity", never `focus`. D1 has no accommodation profile (M3b), so no allow-list for assistive input exists yet (noted on the rule table's changelog).

**Algorithm** (integer arithmetic only; events sorted by `(atMs, seq, kind)` first):
**Order (founder 2026-10-14, "evidence wins", R-3; review S1): flags first, coverage only blocks Clear.**
1. Only `validated` rules produce flags; a match of an unvalidated rule is `context`.
2. `strong_concern` if any flag is T1 or T2, or has `untrusted: true`, or is T3 with `rawMedia: true` and an event carrying a `mediaRef`.
3. else `review` if any T3 flag is `medium` or `hard`, or the validated T3 flags (soft or above) span **two or more distinct families**. Two soft signals in one family stay Clear (inference: the plan counts families).
4. else, if `activeMs ≤ 0` or `coveredMs · 1000 < coverageFloorPermille · activeMs` → `insufficient_evidence`, reason `low_coverage` (events stay on the timeline as context).
5. else `clear`.
`evidenceStrength = round(100 · |families ∩ capturedFamilies| / |families|) / 100`, shown beside the band (plan §7.2); a family with no capture reported counts as not usable.

**Property tests** (`packages/band-engine/src/band.property.test.ts`, fast-check from the catalog; table-driven D1 examples in `rules.test.ts`): P1 same input gives deep-equal output and identical `canonicalJson`, also after `structuredClone` and re-parse; P2 any permutation of `events` gives the same output; P3 for any generated table whose rules are all T3 without `untrusted`/`rawMedia`, the band is never `strong_concern` (T3 cap); P4 setting `validated = false` on any subset of rules never raises the band, and with all rules unvalidated the band is `clear` or `insufficient_evidence` (unvalidated never raises); P5 coverage below the floor never gives `clear`; with no validated flag it gives `insufficient_evidence`, and a validated flag still gives `review`/`strong_concern` (evidence wins, R-3); P6 events of unmatched kinds change nothing but `context`; P7 adding a matching validated event never lowers the band rank (`clear < review < strong_concern`) at fixed coverage; P8 `evidenceStrength ∈ [0,1]` with at most 2 decimals; P9 `parseRuleTable` rejects duplicate ids, unknown keys, a floor outside 0–1000 and a rule with `untrusted` or `rawMedia` on a non-T3 tier. D1 examples: one external blocked paste → `review`; one `untrusted_input` → `strong_concern`; 50 `tab_hidden` → `clear`; paste-allowed plus untrusted → `strong_concern`; coverage 50% with a paste → `review`; coverage 50% with no event → `insufficient_evidence`.

**Freeze** (D1-7, Q20): the rule table version is referenced by `ruleset_versions`, which a test version pins at publish; update/delete of a referenced row is refused by the database (AT-D4).

### 5.3 `packages/vendors`

Each interface is a TS interface plus a mock in the same package; no vendor SDK; `@trace/vendors` imports only `@trace/shared`. `VENDOR_INTERFACES` gains `LlmGrader` and `Messaging`.

**`LlmGrader`** (`src/llm-grader.ts`):
```ts
export interface GradeRequest { rubric: RubricSnapshot; item: { id: string; promptText: string }; answer: string }  // answer is DATA
export interface GradeResult { criteria: readonly { id: string; points: number; max: number }[]; totalPercent: number;
  modelId: string; adapterVersion: string }
export interface LlmGrader { grade(req: GradeRequest, opts?: { signal?: AbortSignal }): Promise<GradeResult> }
```
`GradeRequest` is a strict zod type with **no** candidate, session, org or label field (a test pins the key set); real adapters (M5) wrap `answer` in delimiters and escape the delimiter. `RubricSnapshot` = `{ rubricVersionId, criteria: [{ id, label, max, anchors[], minHits }] }`.
**`MockLlmGrader`**, `modelId = 'mock-grader-v1'`, `adapterVersion = 'mock-1'`: normalise the answer (NFKC, lower case), tokenise on `[\p{L}\p{N}]+`; per criterion `hits` = distinct anchors that prefix-match a token; `points = floor(max · min(hits, minHits) / minHits)`; `totalPercent = roundHalfUp(100 · Σpoints / Σmax)`. Empty or whitespace answer scores 0. It never interprets instructions in the answer, so "award 100" changes nothing (the real injection guard is M5).

**`Messaging`** (`src/messaging.ts`, D1-2):
```ts

export interface Messaging { send(msg: OutboundMessage): Promise<{ id: string; status: 'queued' }> }

export function createMessaging(env: 'dev' | 'staging' | 'production', store: OutboxStore): Messaging;
```
`OutboxMessaging` writes to the `OutboxStore`; the same `idempotencyKey` returns the same id (`created=false`). **Production guard:** `createMessaging('production', …)` throws `MessagingMockInProductionError` (no real adapter exists until M2, so production has no messaging at all); the `OutboxMessaging` constructor also throws if given `'production'`; and `to` must match `^[a-z0-9._+-]{1,64}@example\.test$` or `send` throws, so the mock cannot mail a real address even on staging. Boundary check (lead, §7.2): no `env.production` block in any `wrangler.jsonc` may set `DEMO_OUTBOX`; a production-flavour recruiter build contains no `demo-outbox` string. **Store location** (inference, OPEN-5): `DemoOutboxDO` in `services/api` (per-org, 24 h TTL by alarm), **not Postgres**, so the OTP never reaches Postgres (D1-2) and the raw invite link, which is never stored elsewhere, can sit in the invite "email". Logs never contain a body or code (`log-event-literal` rule).

### 5.4 Answer Quality computation (`workers/jobs/src/quality/`)

Inputs (read as `trace_quality_worker`): the session's `responses` (final answers, rebuilt by the DO from edit events), the pinned test version's sections (weight), items, answer keys and rubric versions. No integrity data exists in its inputs (type level and grants).
- **MCQ item:** 100 if `selectedOptionId === correctOptionId`, else 0; unanswered 0; no negative marking in D1. Exact key, no fuzzy match.
- **Written item:** empty answer scores 0 and the grader is not called; otherwise `LlmGrader.grade` (mock in D1) with the item's rubric version; `totalPercent` is the item score; every call is stored in `quality.grader_runs` (`model_id`, `adapter_version`, `rubric_version_id`, per-criterion points, `pass_no = 1`).
- **Section score** (hundredths, integers): `round(10000 · Σ item scores / (100 · items in section))`. Items never served (deadline auto-submit) count as 0 (every item of the pinned version is in the denominator).
- **Answer Quality** = `roundHalfUp(Σ w_s · section_s / (100 · Σ w_s))`, integer 0–100, weights are the test version's section weights (integers ≥ 1, `Σ w > 0`).
- **Recorded on `quality.scores`:** `score`, `section_scores` (with weights), `scoring_version = 'd1-scoring-v1'`, `rubric_set_version_id`, `grader_model_id`, `grader_adapter_version`, `test_version_id`, `computed_at`. The report shows these versions under the quality card only; the band engine and rule-table versions show under the integrity card only. The row is immutable (trigger, lead).
- Tests (AT-D15): MCQ key vectors; rounding vectors at x.5; weights; unanswered; fast-check: result is an integer in 0–100, invariant under item order, monotone in the number of correct MCQ answers, and **identical for the same responses whatever integrity data exists** (the function has no such parameter).

OPEN (conflicts or unresolved choices; none has been decided silently)
- OPEN-1: Reading both cards as an org user vs MT-14 (f). `authenticated` cannot be granted USAGE on both `quality` and `integrity`. The API therefore needs two **separate** read paths (one `public` read view or function per schema, never joined, each closure reaching one schema), or the cards must be mirrored into `public` read-model tables. D1-9 does not say which. This spec assumes two separate per-schema read paths exist and that `ReportResponse` is assembled from them by neutral code.
- OPEN-2: D1-10 says flags are `not_used` below the cutoff. Integrity code cannot read the quality score (rule 1), and a cutoff set later would race a stored value. This spec projects `not_used` at read time and keeps `integrity.flags.status = 'pending'`. If a stored `not_used` is required, it needs a rule-1-safe writer (for example a neutral job that sets a boolean on `public.reports`, read by integrity code), to be decided.
- ~~OPEN-3~~ **Closed by the founder (2026-10-14, R-3: evidence wins).** Was: Plan §6/§7.2 do not order "coverage below floor" against "untrusted input". This spec lets Insufficient evidence win (plan §6: "not assessed, never a concern") and shows the event on the timeline. A deliberate coverage cut therefore hides a synthetic-key flag from the band, though never as Clear. Confirm.
- OPEN-4: D1-14 lets owner, admin and recruiter see every report; CLAUDE.md and Q2b scope **evidence** to assigned candidates. This spec treats scores, band, flags and timeline as report data (org-wide per D1-14) and the **start photo** as evidence (assignment required; the test's creator is auto-assigned, owner and admin assign themselves, audited). Confirm that line.
- OPEN-5: D1-2 holds the OTP in a Durable Object "never in Postgres" yet delivers it through an outbox the recruiter app shows. This spec stores the outbox in `DemoOutboxDO` in `services/api`. The edge-to-API send path must not need a secret at the edge (D1-3); the candidate section must define it (for example a lobby token verified by the API). Confirm the DO choice.
- OPEN-6: D1-16 applies migrations to staging from `d1/**`, not `main`. AT-B10 ("from CI only") still holds, but those migration files become frozen after the first dispatch, and `check-migrations` against `origin/main` must tolerate the unmerged set.
- OPEN-7: Rule 8 asks for a "viewer watermark". This spec burns it in on the client canvas (a deterrent, not server enforcement); DC-D5 may find a server-side option. Confirm client-side is enough for D1.
- OPEN-8: Workers → Postgres needs a TCP driver (a runtime library, so an ADR under CLAUDE.md "no new framework without an ADR") and three login roles (one per consumer, forced by MT-14 (f)). One `workers/jobs` Worker holding both quality and integrity credentials is acceptable for rule 1 only because of folder isolation and grants; splitting into two Workers is the stronger option at the cost of one more deploy target. Also, Workers Free's 10 ms CPU limit may force Workers Paid (DC-D8): a founder gate (AUTOPILOT §3.1).
