## 1. Scope and lead decisions
### 1.1 The slice (exit gate, build-order.md:37)
A recruiter creates a test (written + MCQ) and invites a candidate by link. The candidate takes it in the browser with a server-held timer, a start photo and autosave. The result shows **Answer Quality** (0–100, mock grader) and the **Integrity band with an evidence timeline as two separate results**. A reviewer opens the report. It is deployed on staging (`*.workers.dev` / Pages), with synthetic data only. **Exit gate:** the full flow passes an automated E2E test on staging, plus a 5-minute screen recording.

### 1.2 Decisions (lead, AUTOPILOT §4; founder answers where marked)
| # | Decision | Why / source |
| --- | --- | --- |
| D1-1 | **Synthetic-only by construction.** D1 stores **no candidate name, phone or free-text identity**. Each invitation has a generated label (`Candidate 1`, `Candidate 2`, …) and a contact email that a DB CHECK limits to `^[a-z0-9._+-]{1,64}@example\.test$` (RFC 2606 reserved), so no real person can be invited. M2 replaces this with encrypted contacts (`candidates`, `candidate_contacts`, KMS) | Rule "no PII", plan's KMS rule for sensitive fields; staging is synthetic-only (build-order.md:37) |
| D1-2 | **Candidate auth = invite link + email OTP** (ADR-017). Link token: 256 random bits, only its SHA-256 is stored, and it never starts a session without an OTP (Q32). OTP: 6 digits, 10 min, 5 attempts, resend after 30 s (Q47). It is held in a Durable Object, never in Postgres. **Delivery is the `Messaging` mock:** it writes to a per-org **demo outbox** that the recruiter app shows on non-production builds only. The outbox only ever holds `@example.test` recipients (D1-1). Production refuses the mock (a boundary check plus a runtime guard) | ADR-017, build-notes Q32/Q47; Messaging is M2; avoids a test-only secret path |
| D1-3 | **Candidate token** = ADR-030 format (ES256, `typ` `lobby`/`session`, `kid`, `nonce`, short `exp`). `services/api` signs (Worker secret `CANDIDATE_TOKEN_PRIVATE_JWK`; check-staging-secrets allow-list updated). `workers/edge` verifies with the public JWK (a plain var) and **holds no secret**. In D1 **the candidate never reaches Postgres**: there is no `trace_candidate` RLS path. ADR-030 → "Accepted (autopilot) for token format and edge verification"; the gateway / `SET LOCAL ROLE` part stays M3a | ADR-030, ADR-027, CLAUDE.md (no service keys in candidate DOs) |
| D1-4 | **Session Durable Object** `SessionDO` (SQLite-backed) in `workers/edge`. It holds the server timer, the served items, edit events with `(stream_id, seq)` dedupe, heartbeats, client signals, and the deadline auto-submit (alarm, +60 s grace for in-flight saves). Answers are rebuilt from edit events. The test package is read from R2 at session start; the DO never reads Postgres. On submit the DO enqueues **one mirror message** (Queue `trace-session-mirror`); `workers/jobs` writes Postgres idempotently. If Queues are unavailable on the plan (DC-D2), fall back to a service binding plus a DO-alarm retry | ADR-016, Q38/Q41/Q43, CLAUDE.md "server holds the truth" |
| D1-5 | **Start photo (founder 2026-10-14):** an on-screen **oval face guide**. Everything outside the oval is blurred on the device (canvas) before upload. Only the processed JPEG leaves the device. Upload goes through the edge Worker (type and size limits) to R2 `media/{org}/{session}/start_photo.jpg` (deterministic key). The reviewer sees it only through a **5-minute signed link with a viewer watermark**, and every view writes `audit_log` `media.view`. No face matching. Camera frames never leave the device | Rule 8, plan:486-498, founder answer |
| D1-6 | **Integrity inputs (founder 2026-10-14):** only deterministic browser facts may raise the band: `paste` / `drop` (T3, caps at Review) and `untrusted_input` (synthetic `isTrusted = false` key or input events; Strong concern per plan §6). `tab_hidden` and `fullscreen_exit` are **context only** (`validated = false`). Coverage = heartbeat coverage of the session; below the floor → **Insufficient evidence** (never Clear). Connectivity gaps are labelled "Connectivity", never focus loss | Rule 3, plan:258-293, 340-347 |
| D1-7 | **Band engine** `packages/band-engine`: pure TypeScript, no I/O, deterministic. The rule table is **versioned data** (`integrity.band_rule_versions`, `validated` flag per rule), referenced by `ruleset_versions`, and frozen at publish (Q20). Same inputs → same band, plus evidence strength 0–1. A pulled-forward minimal subset of M4 | Rule 3, build-order.md:70-73 |
| D1-8 | **Answer Quality:** MCQ exact-key scoring and written answers through the `LlmGrader` interface (`packages/vendors`) with the deterministic `MockLlmGrader` (`model_id = mock-grader-v1`). The answer is passed as delimited data with no candidate identity. A versioned rubric. Score 0–100 is the weighted section average. Stored in `quality.*` by `trace_quality_worker` only | Rule 1, plan §7.1, build-order.md:37 |
| D1-9 | **Two results, never blended (rule 1):** `quality.*` and `integrity.*` stay separate (non-overlapping worker roles; MT-5/MT-14 apply). `public.reports` holds one FK to each card (founder ruling, build-notes §0 "Rule 1 catalog check"). No view, function or trigger reaches both schemas. The UI shows two equal cards and no combined number | Rule 1 |
| D1-10 | **No rejection, no decisions (rules 2, 4, 6):** D1 has no reject, decision, notice or appeal object. The test has an Answer Quality **cutoff**: below it the integrity card reads "Not reviewed (below cutoff)" and its flags are `not_used`. Flags stay `pending` (no confirm action in D1; M6). No bulk action exists | Rules 2, 4, 6 |
| D1-11 | **Candidate sees a receipt only** (`receipt_ref`), never a score or band (rule 5's `report_candidate_view` is M6) | Rule 5 |
| D1-12 | **Under-18 (rule 9):** the inviter states 18+ (`adult_confirmed_by_inviter`, default unknown) and the candidate self-declares at the age step. If either says under 18, the invitation goes to `blocked_age` and no session can start (DO check + DB CHECK/trigger). Only a boolean and its source are stored, never a date of birth (MT-3) | Rule 9, Q37 |
| D1-13 | **Consent:** order is link → OTP → age → consent → camera/photo → rules → test. No `getUserMedia` before a consent row exists (Q36). The notice is an immutable `notice_versions` template; the rendered text's SHA-256 is stored per consent | Q35/Q36 |
| D1-14 | **Assignments (minimal):** `assignments(scope = 'test')`. A reviewer sees reports only for tests assigned to them; owner/admin/recruiter see every report in the org; hiring_manager sees nothing in D1 | Q2, ADR-029 |
| D1-15 | **Pulled forward, minimal:** tables from M1 (tests, test versions, sections, item versions, answer keys, rubrics, ruleset versions), M2 (invitations, assignments), M3a (sessions, consents, session items, responses, media objects, notice versions), M4 (band rule versions, signals, flags, integrity results), M5 (quality scores, grader runs) and M6 (reports, `media.view` audit). Each keeps the build-notes §4 column names where they exist, so the full milestones extend rather than replace them. **Invariant 12 ("no score/band column in M0–M3") is amended for D1** and recorded in build-notes "Autopilot changes" | build-notes §4 |
| D1-16 | **Staging (founder 2026-10-14):** a manual `workflow_dispatch` job deploys `d1/**` or `milestone/**` to `staging`; the founder widens the environment's branch policy. `main` stays CLOSE-only | Founder answer |
| D1-17 | **E2E:** Playwright (dev tooling, no ADR; build-notes:179) in a new workspace package `e2e/`. One spec runs the whole slice against the local stack in CI and against staging by `workflow_dispatch`. The recording is made from the staging run | build-order.md:37 |
